## Feature

Track B -- Phase 3 input quality: reduce Phase 3 input tokens by >= 40% (from ~5.1M
tokens/run on the Koopmans reference run) without degrading doc quality.

## Problem Statement

The LobsterProfileExportKoopmansTest reference run consumed 5,126,576 input tokens
across 61 Phase 3 calls (deepseek/deepseek-v4-pro). Four compounding root causes:

1. **Hint-only dispatch (biggest)**: `_complete_core_generation` (harness.py:3144-3150)
   drops ALL context files when the provider supports tools (`context_files = []`).
   The model discovers the 348-535 KB evidence pack through 50 KB `read_artifact`
   reads. Each tool turn replays the full prior conversation — O(n^2) growth.
   On a 10 KB/turn pack, 10 turns = 55 KB extra; on a 500 KB pack, 10 turns = 2.75 MB
   extra. This is the dominant cost driver.

2. **BASELINE too broad**: `BASELINE_BUNDLE_SECTIONS` (harness.py:113-120) includes
   `{GROUP_SUMMARY, COMPONENTS, EXECUTION_FLOW, CROSS_GROUP_REFS, RISK_FLAGS,
   UNCLASSIFIED_OR_EXTRA_FINDINGS}`. These 6 sections cover 51.1% of all Phase 2
   bytes in every pack — regardless of which doc is being written. The shared floor
   is ~349 KB, which is 87-89% of the median pack size.

3. **Parser 3 defects (104 KB UNCLASSIFIED per run)**:
   - `#### HIGH` / `#### LOW` sub-headings inside RISK_FLAGS break the parser, routing
     ~6.8 KB of risk content to UNCLASSIFIED per run.
   - `CROSS_CHUNK_FINDINGS` (harness-generated by `_phase2_cross_chunk_synthesis`) is
     intentional Phase 2 output but not registered in `PHASE2_SECTION_NAMES`, routing
     75,950 bytes to UNCLASSIFIED per run.
   - Plugin ANALYSIS_GUIDE mandates sections like `DEBUG_TESTING_EVIDENCE`,
     `CHANGE_IMPACT_EXTRACTION` that the harness has never registered: ~21 KB routes
     to UNCLASSIFIED. Because UNCLASSIFIED is in BASELINE, all 104 KB reaches every pack.

4. **Three waste sources**:
   - `_doc_pack_manifest.json` (155 KB) included in Phase 3 context but the model
     uses the pack files directly; the manifest is bookkeeping for the harness.
   - `_source_coverage.json` CSV indexes (3.1 MB) added as starter files by
     `_engineering_fact_context` even when `_source_coverage.json` is absent — the
     code builds a fallback CSV list anyway. Model receives 3 MB of CSV index paths
     for files that don't exist.
   - `_doc_pack_09_EXECUTIVE_SUMMARY.md` (349 KB) built by Phase 2.8 for every run
     but never read by any Phase 3 code path (`required_docs` does not include 09).

## Definition of Done

- Phase 3 input tokens per run drop by >= 40% on a re-run of the Koopmans project
  (from ~5.1M tokens) with no quality regression on human spot-check of the 10 docs.
- UNCLASSIFIED bytes per group analysis file drop to <= 5 KB.
- Doc packs 01 and 02 differ by >= 30% by byte count (currently identical).
- Pack 09 is no longer built.
- Manifest and CSV indexes removed from Phase 3 context.
- All 590 existing tests pass; new tests cover each fix.

## Out of Scope

- Phase 1 investigation, Phase 2 analysis, Phase 2.6 scorecard — untouched.
- RAG pipeline, dashboard, scanner CLI — untouched.
- Doc quality improvements beyond what correct context assembly provides.
- Provider-specific optimizations (caching, batching) — orthogonal.
- Phase 2 repair (`_phase2_targeted_repair`) — separate track.
- The 4 PRD out-of-scope bugs (validator parentheses, incremental-regen cache,
  preamble stripping, scorecard weight-format mismatch) — separate slices.

## Solution Rationale

The Fable agent investigation confirmed the hint-only dispatch is the primary driver:
when tools are available, `_complete_core_generation` passes `context_files = []`
and the model pages the pack iteratively. Evidence registry doc slices
(`_evidence_registry/doc_slices/`) are dominated by 120-char truncated raw JSON dumps
and are not useful as alternative context. The correct fix is to push a targeted
100 KB starter pack (just the sections the doc needs) and let tools handle drill-down.

The parser fix must land first (Slice 1) before BASELINE can be reduced (Slice 2),
because removing UNCLASSIFIED from BASELINE would silently discard 76 KB of
CROSS_CHUNK_FINDINGS unless the parser first routes it correctly.

## Assumptions and Risk

- The Koopmans reference run is representative of production runs (61 calls, 10 docs,
  multi-chunk groups).
- deepseek/deepseek-v4-pro is the production model; behavior with other providers may
  differ (but the token reduction applies to all tool-capable providers).
- Targeted pack push (100 KB cap) assumes GROUP_SUMMARY + doc-specific sections stay
  within cap for all current docs. If a doc's section set exceeds 100 KB, the harness
  must truncate to GROUP_SUMMARY only.
- BASELINE reduction to GROUP_SUMMARY only assumes each doc's `phase2_sections` in
  `doc_catalog.yaml` is correctly specified. If a doc's sections list is too narrow,
  the pack will be underspecified. Doc 01 and 02 currently resolve to the same section
  set — Slice 2 must differentiate them.

## Critical Areas Touched

- Harness pipeline phases (`knowledge_base/mcp-server/src/mcp_server/providers/custom/harness.py`)
  — all three slices. `/inspect` required for each slice.
- `data/doc_catalog.yaml` — Slice 2 only (no pipeline phase files, but affects pack assembly).
- `knowledge_base/CLAUDE.md` and `.agent/system/mcp-workflow.md` — Slice 3 docs update.

## Risk if Wrong

- Hint-only dispatch fix (Slice 3): if the 100 KB starter pack is missing critical
  context the model would have found via tool paging, doc quality degrades (missing
  sections, wrong cross-references). The acceptance run on Koopmans catches this.
- BASELINE reduction (Slice 2): if a section is removed from BASELINE that a doc
  genuinely needs, the doc will be underspecified and may fail obligation checks.
  The pack differentiation test (01 vs 02 differ by >= 30%) guards against this.
- Parser fix (Slice 1): additive only — content that parsed correctly before still
  parses correctly. Only UNCLASSIFIED content moves to named sections.
