| Admin surfaces use shared UI only | No admin page defines its own button/input/dialog classes. ## Lessons Learned / Gotchas

- **A setting in `src/config.py` is unreachable in a deployed stack unless it is also listed in that service's `environment:` block in `docker-compose.yml`.** Compose passes only the variables it names; `--env-file` populates interpolation, it does not export the file into the container. Found 2026-08-26 with five settings that had been silently inert since they were added: `RUNTIME_TOOL_LOOP_MAX_ITERATIONS`, `RUNTIME_TOOL_MAX_PARALLEL_CALLS`, `RUNTIME_LLM_FALLBACK_ENABLED` (so the EP-005 slice 4 opt-in could not be switched on at all in deployment), `TALEND_TMC_REQUEST_TIMEOUT`, `TALEND_TMC_COMPONENT_METRIC_RUN_LIMIT`. The failure mode is the worst kind: the operator sets the value, nothing errors, the default keeps running. When adding a setting, add the passthrough in the same commit; when a knob "has no effect", check the `environment:` block before the code.

- **In an env file the LAST assignment of a key wins, so a duplicate silently reverts the earlier one.** `deploy-client.sh` wrote `TRUSTED_PROXIES=127.0.0.1,172.16.0.0/12` (with a comment explaining that the Compose bridge range must be trusted or per-IP limits collapse) and then `TRUSTED_PROXIES=127.0.0.1` forty lines further down under "Network hardening". The second won, so every rate limit was keyed on the frontend container -- the exact bug the first line was written to prevent. Fixed 2026-08-26. When editing generated env files, `grep -c '^KEY='` before assuming the value you can see is the value in force.

- **`deploy/mcp-server@.service` is retired; MCP runs as the `mcp-server` Compose service.** The unit still exists in the repo and still points at `$REPO_ROOT/venv/bin/python`, a host virtualenv the deployed stack does not create and `deploy-client.sh` never installs. RUNBOOK step 8 used to tell operators to `systemctl restart mcp-server@<client>.service` after an env change, which silently does nothing. Env changes to a Compose service need `up -d` (recreates with the new environment), not `restart` (reuses it) and not systemd.

- **`docker compose up -d` starts EIGHT services, not the seven in the EP-001 health boundary.** `mission-control` has no profile gate, binds `127.0.0.1:${MC_PORT:-9100}`, and is the operator-side heartbeat aggregator rather than a per-client service. Verification steps that expect seven containers misreport. From 2026-08-26 `deploy-client.sh` generates `MC_API_KEY` (the Compose default was a shared `mc-dev-local-secret`) and offsets `MC_PORT` so two stacks on one host do not collide.

- **The documents collection runs Qdrant strict mode, so EVERY payload field a filter touches must have an index -- there is no scan fallback.** `strict_mode: {enabled: true, unindexed_filtering_retrieve: false, unindexed_filtering_update: false}` means a `FieldCondition` on an unindexed key returns HTTP 400 (`Index required but not found for "<field>" of one of the following types: [...]`), never a slow scan. From 2026-08-25 the index set is declared ONCE in `PAYLOAD_INDEXES` (`src/retrieval/vector_store.py`) and `ensure_collection` loops over it; `test_every_filtered_payload_key_has_an_index_declared` fails the build if a module importing `COLLECTION_NAME` filters on a key missing from the map. Before this, eight indexes existed against ten filtered fields: `expand_neighbor_chunks` (`chunk_index`) 400ed on every single query and its handler swallowed the error, so neighbour expansion was dead in production for an unknown length of time while looking enabled; `clone_revision_artifact_points` (`project_id`) has no try/except and failed outright. **The index type is load-bearing**: `chunk_index` is written as an int, so it needs INTEGER -- a KEYWORD index leaves the 400 in place. If you add a filter, add the field to the map in the same commit.

- **The backend does NOT use the local `qdrant` Compose service.** `QDRANT_URL` points at a managed Qdrant Cloud cluster (`*.europe-west3-0.gcp.cloud.qdrant.io:443`). The local `intodata-kb-v2-qdrant-1` container still exists and still holds a `documents` collection -- empty, 2 indexes, no strict mode. Any manual `curl` against `localhost:6333` therefore succeeds against the wrong database and looks like a successful fix while production is untouched. Always resolve the target from `docker exec <backend> printenv QDRANT_URL` before running collection surgery, and confirm the point count matches production before believing a result.

- **There are two unrelated "runtime" subsystems and the UI badge reports the wrong one.** (1) The *live provider* path (EP-004): `runtime_provider_key` / `runtime_provider_health_url`, dispatched via `src/runtime/client.py:execute_runtime_tool`, consumed by the legacy V1 `src/generation/agent_loop.py`, and surfaced by `GET /api/v1/runtime/status` -> the `RuntimeStatusIndicator` badge. (2) The *stored* path: `StoredRuntimeProvider` reading the `runtime_*` Postgres tables, imported DIRECTLY by `src/harness/evidence.py` and never consulting `runtime_provider_key`. With `AGENT_RUNTIME_V2_CANARY_STAGE=full_standard` all chat traffic runs the V2 harness, i.e. path (2). Because `RUNTIME_PROVIDER_KEY` is empty, the UI reads **"Live runtime disabled"** while `read_runtime_evidence` works perfectly -- confirmed 2026-08-25 by calling `StoredRuntimeProvider.list_executions` directly and getting 20 real executions. Do not diagnose runtime-tool availability from that badge; it tracks a subsystem chat no longer uses. The badge itself is an open cosmetic bug.

- **`runtime_log_events` being empty is not a misconfiguration.** `talend_tmc.py:808-854` downloads logs only for FAILED runs (capped by `talend_tmc_failed_log_run_limit`). With 3958 `success` + 5 `unknown` and zero failures ingested, `search_runtime_logs` correctly returns 0 hits. Check the execution state distribution before hunting for a broken log pipeline.

- **`query_usage.project_id` has no foreign key to `projects`.** Six tables cascade on project delete (`generate_runs`, `generation_experiments`, `project_connector_bindings`, `project_doc_rag_hashes`, `project_group_scan_hashes`, `scan_runs`); `query_usage` does not, so deleting a project leaves orphaned usage rows unless they are removed explicitly. Also note `sudo docker exec` needs `-i` to accept a heredoc -- without it the SQL never reaches psql and the command reports success having done nothing.

- **User-typed free-text request fields should not carry arbitrary `max_length` caps unless there's a real technical reason.** `PackDraftAssistRequest.instruction` (`src/api/routes/harness_packs.py`) had `max_length=4_000` with no stated rationale, while the ordinary chat `QueryRequest.query` field has no cap at all. When a user pasted a longer request into the Pack Workbench composer, they got a raw, unhandled FastAPI/Pydantic 422 (`String should have at most 4000 characters`) with no client-side warning first — confusing because nothing in the UI indicated a limit existed. Fixed 2026-07-23 by dropping the cap to match `QueryRequest.query`'s precedent. If you're about to add or keep a `max_length` on a free-text instruction/message/query field, check whether an equivalent field elsewhere in the app is already unbounded — if so, match it rather than inventing a new limit, and if a cap is genuinely needed, enforce it client-side (with a visible counter) so users get instant feedback instead of a failed round trip surfacing raw Pydantic error text.

- The declarative `Base` (`src/db/base.py`) auto-declares `created_at` AND `updated_at` on EVERY model. So any migration that `create_table`s a new model-backed table MUST include both columns (`TIMESTAMPTZ NOT NULL`, `server_default=sa.func.now()`) — otherwise every SELECT on that table 500s with `asyncpg UndefinedColumnError: column <table>.created_at does not exist`. This bit `runtime_component_metrics`, `runtime_artifacts`, `runtime_connections`, `runtime_job_dependencies` (migrations 037/043 omitted them; fixed in 048). When adding a table or reviewing a create_table migration, cross-check the two `Base` timestamp columns are present.

- **FIXED 2026-07-07** (was: "flaky pre-existing failures, root cause unclear"): the `TestRetrievalLadder`/`TestLadderEntityMatching` tests in `tests/test_generation/test_conversational_rag.py` didn't mock `analyze_query_async` — they hit the real live LLM classifier chain (Kimi/Ollama). For borderline queries (e.g. "What does tDBOutput_1 do on failure?"), the classifier nondeterministically returned `search` or `project_detail` across identical calls (confirmed via 10x live sampling). When it returned `project_detail`, execution fell into the METADATA action path (`fetch_metadata` → `get_project_detail`), which these tests' `AsyncMock` db fixtures were never set up to handle, producing `AttributeError: 'coroutine' object has no attribute 'id'` at `src/retrieval/metadata_retriever.py:119`. Fixed by pinning `analyze_query_async` (and `detect_runtime_keywords`, added 2026-07-07) to a fixed `QueryAnalysis(action=Action.SEARCH, ...)` in all 8 affected tests — matching the mocking pattern other test classes in the same file already used. Tests are now 100% deterministic and ~20x faster (no network calls). **Lesson for future test-writing in this file**: any test that calls `run_conversational_rag`/`run_conversational_rag_stream` without mocking `analyze_query_async` is exercising a live, non-deterministic LLM call — always pin it unless the test is specifically about classifier behavior (that belongs in `test_intent_classifier.py`).

- **`backdrop-filter: blur` is one of the most expensive CSS properties** — never use it on per-node or per-group elements in graph views. Even `blur(1px)` forces the GPU to re-blur whatever is behind every element on every paint. For ~10 elements this is a constant frame-rate killer; the visual effect at 1px is also imperceptible. Use a flat gradient or a colored border instead.
- **Infinite CSS animations (`animation: ... infinite`) cause constant repaint loops** — even when the user is idle, the GPU keeps painting every frame. In ReactFlow specifically, dashed/animated edge styles like `.react-flow__edge.animated path { animation: edge-flow ... infinite }` paint forever for every dashed edge in the visible graph. Either remove the infinite animation entirely or scope it to a JS-set `data-animated` attribute opt-in.
- **Per-node mount animation re-fires on every layout change in ReactFlow** — if a CSS class like `.topo-node-enter { animation: node-enter 0.3s }` is applied via `className` on each node component, every direction/compact/expand-collapse toggle remounts nodes and the keyframe re-runs across the entire visible graph at once, producing a visible "wash" of animation. Don't put per-instance entry animations on graph nodes.
- **ReactFlow's `setNodes` reconciles every node** — guard hover/search effects with a `useRef` that early-outs when the new state matches the previous (`prevHoverRef.current`, `prevSearchRef.current`). Without this, any unrelated re-render that re-enters the same hover state still rewrites every node object, triggers full reconciliation, and produces visible "ripple lag" on large graphs. Pattern: `if (state === prevRef.current) return; prevRef.current = state;` at the top of the effect.
- **`setNodes((nds) => nds.map(...))` MUST return same-reference nodes for unchanged ones** — the early-out alone is not enough. Even when we *do* run the effect (because the hovered node actually changed), the inner `map` still rewrites every node ref by default. With `React.memo` on the node components, returning the same node reference (or at least the same `data` reference) for nodes whose dimming/highlight state didn't actually change makes the per-component render skip. Pattern: `if (n.data.dimmed === newDimmed && n.data.highlighted === newHighlighted) return n;` before the `{ ...n, data: { ... } }` spread. Same idea for `setEdges` against `e.style?.opacity`. On a graph with 80+ nodes this is the difference between "ripple lag on every hover" and "instant". Use the destructuring trick `const { opacity: _drop, ...restStyle } = e.style ?? {}` to *remove* a key rather than set it to `undefined` (the latter still produces a new style object).
- **MiniMap re-renders all nodes on every viewport movement** — gate it on a node-count threshold (e.g. `visibleNodes.length <= 150 || isCollapsed`). On heavy graphs the minimap is both expensive and useless because every node is a pinhead.
- **Inline `transition: opacity 0.3s ease` is dangerous combined with hover dimming** — when hover dimming rewrites the entire node array, every node has to animate its opacity for 0.3s simultaneously, which is the visible "ripple lag". For graph views prefer instant dimming (no transition); the snappy feel beats the visual polish.
- **Same-reference dimming optimization is undone by the layout effect unless laid-out nodes carry explicit `dimmed: false, highlighted: false` defaults** — `setNodes([...bgNodes, ...laid])` writes nodes whose `data.dimmed` is `undefined`. The hover effect's same-reference fast path is `if (n.data.dimmed === !isMatch && n.data.highlighted === isMatch) return n;` — `undefined !== false` strict-equality fails for every freshly-laid node, so the entire graph gets rewritten on the FIRST hover after any layout change. Initialize the defaults: `laid.map((n) => ({ ...n, data: { ...n.data, dimmed: false, highlighted: false } }))` before calling `setNodes`. After the first hover all nodes have explicit `false`/`true` and subsequent hovers are fast — which is exactly what made round 3 of the topology perf pass invisible to most projects but lethal on `scherpenhuizen-talend`.
- **ReactFlow `fitView` animations stack when fired from multiple effects on the same frame and dominate frame time on heavy graphs** — the layout `useEffect` calls `fitView({duration: 300})` and the search `useEffect` calls `fitView({duration: 400})`; both can fire when `groupMembership` rebuilds with the same shape or when the user types fast. Gate them with a "last-fit-key" `useRef` keyed on the meaningful layout identity (`${selectedProject}|${direction}|${compactMode}|${nodeCount}`) and only call `fitView` when the key actually changed. Reset the ref on project switch so the new project still gets its initial fit.
- **Search auto-fit must not run on every keystroke when the match set is large** — typing one letter in a project that matches 40 nodes triggers a 400ms `fitView` zoom-fit across the entire viewport, and the animation stacks with subsequent keystrokes. Cap on `searchMatchIds.size <= 8` so single-letter searches just dim the rest; once the user has typed enough that the match shrinks to a useful size, the auto-fit kicks in. This matches every other code-search UI.
- **JWT cookie auth across services**: RAG backend (port 8000) issues cookies. Next.js (port 3000) proxies auth endpoints and forwards cookies to FastAPI. MCP server (port 8002) validates JWT independently using shared `JWT_SECRET_KEY`. Dashboard (port 8001/nginx) forwards cookies via `proxy_set_header Cookie`. ### Runtime-intent gate (Slice 1 of chat response-time restoration, 2026-07-07)

- **`RAGContext.allow_runtime_tools` is the single gate for tool-loop entry — do not reintroduce a `precomputed_answer is not None` check as a proxy for it.** Before this fix, the streaming handler used `precomputed_answer is not None` to decide whether a turn was "terminal" (skip the loop); this silently broke because streaming (`precompute=False`) leaves `precomputed_answer=None` even for chitchat/metadata turns that were never meant to touch the loop. Any new answer path added to `_prepare_rag_context` must explicitly set `allow_runtime_tools` (default `False` is correct for anything that isn't the runtime-gated branch or reusing a still-True context) — never rely on `precomputed_answer`'s nullness as an implicit signal.
- **The runtime gate (`runtime_gate = analysis.runtime_intent OR detect_runtime_keywords(query)`) is computed exactly once per turn, in `_prepare_rag_context`, and must stay there.** Both `run_conversational_rag` (REST) and `run_conversational_rag_stream` call `_prepare_rag_context` and trust its `allow_runtime_tools` output — do not duplicate gate logic at either call site; if REST and streaming ever compute the gate differently they will drift and give different answers to the same query depending on entry point.

If you need to add another early-return branch to `_prepare_rag_context`, check whether it belongs before or after this one — action-type branches (METADATA/RESPOND/SUMMARY) correctly stay before it since they're not QA at all; anything QA-shaped that should also skip the ladder belongs here.

### Sniff-buffer streaming + tool-loop live streaming (Slices 2-3 of chat response-time restoration, 2026-07-07)

- **Never check a late-marker/pattern match against only the freshly-flushed slice of a rolling buffer — always check the whole retained pending buffer.** `_drain_stripping_late_marker()` in `conversational_rag.py` originally (in the rejected Slice 2 plan) checked `_NEED_SEARCH_MARKER in safe` where `safe` was only the delta about to be yielded that iteration, with `pending` capped at `len(marker)-1` chars. A marker straddling a flush boundary (part already flushed, part still pending) could NEVER be detected as a whole under that design — a real correctness bug caught by 2 of 3 judges before any code was written, and independently re-derived and fixed by the builder when the AC test failed against a large-single-chunk repro. The fix: `_partial_marker_suffix_len()` computes the longest trailing proper-prefix-of-marker match against the FULL accumulated buffer each iteration (shared implementation with the sniff-phase's `_ends_with_partial_marker`-equivalent logic — do not duplicate the scan between the two phases). Lesson for any future streaming-buffer code in this file: a fixed-offset slice check is not equivalent to a whole-buffer check for a moving-target pattern — always reason about the buffer's full contents, not an arbitrary cut point.
- **`_sniff_stream_sufficiency()` only ever consults the `_CANT_ANSWER_PATTERNS` heuristic on the "stream exhausted while still inside the sniff buffer" path** — this is intentional, not a narrowing. `_SNIFF_BUFFER_CHARS` is set to exactly 200 to match the heuristic's own existing `len(stripped) < 200` gate in `needs_new_search()`, so "the whole answer fit inside the buffer" and "the heuristic's own length gate" line up exactly — an answer that keeps streaming past 200 chars would never have triggered the heuristic under the old blocking code either. Do not add the heuristic check to the "still streaming, buffer full" branch — it would diverge from `needs_new_search()`'s pre-existing semantics.
- **A partially-consumed `generate_answer_stream()` async generator can be legitimately stored across an `await` boundary and a function return** (as `RAGContext.stream_remainder`) so a later caller can resume draining it. This is valid Python but unusual for this codebase — do not try to "simplify" this into re-fetching or caching a `RAGContext` across turns; the generator is single-use and tied to one in-flight HTTP/provider connection. Every early-exit path that decides NOT to resume a sniffed-but-open stream (e.g. the rung-1 `missing_identifiers` override after a sufficient sniff) must call `.aclose()` on it — a leaked open provider stream is the failure mode if this is forgotten.
- **`run_runtime_tool_loop()` (the public, non-streaming name used by REST) is now a thin wrapper that drains `run_runtime_tool_loop_stream()` (the actual async-generator primitive with all tool-execution logic)** — never re-implement tool-call/tool-result/synthesis logic in the wrapper; it exists only so `run_conversational_rag` (REST) and any test that patches `run_runtime_tool_loop` directly keep working unchanged. If you need to change tool-loop behavior, change `run_runtime_tool_loop_stream` only.
- **The final synthesis in the tool loop (after `>=1` tool call, decision ends with plain text) now ALWAYS makes an extra `generate_answer_stream()` call it didn't make before** — previously `decision.text` was delivered directly with zero extra calls; now it's regenerated via streaming so genuine token-by-token delivery is possible (there is no way to "stream" an already-complete string without re-invoking the model). This is a deliberate PRD-mandated latency/cost trade-off (`.plans/02_prd.md` — "ONLY the final synthesis after tool execution should stream via generate_answer_stream()"), confirmed intentional by the Slice 3 Inspector, not a regression to "fix." The ONE case that still short-circuits with zero extra calls: the very first decision call returns text with NO tool calls ever made (`progress` empty) — nothing ran, nothing to stream progress for.
- **Any test that lets the real (unmocked) `run_runtime_tool_loop`/`run_runtime_tool_loop_stream` execute now needs a `generate_answer_stream` fake-async-generator patch in the `src.generation.agent_loop` namespace**, in addition to the Slice 1 lesson about mocking `analyze_query_async`. This bit ~12 existing tests across `test_agent_loop.py`, `test_conversational_rag_runtime_tools.py`, `test_conversational_rag_runtime_insights.py`, and even an unrelated-looking `test_runtime/test_stored_end_to_end.py` (which drove the loop end-to-end and hit a real unmocked provider on the first full-suite run after Slice 3 landed). If you add a new test exercising the tool loop, mock `generate_answer_stream` even if your test doesn't care about the final answer's content — the synthesis tail always calls it now.
- **When a test asserts on `RuntimeLoopOutcome.usage`, explicitly patch `src.generation.agent_loop.get_last_usage`** — the synthesis tail calls `_accumulate_usage(usage, get_last_usage())` against a process-global set by `llm_client.py`; without patching it, a test can pick up stray usage state left by an earlier test/provider call in the same process and produce flaky token-count assertions.

### Nexus harness LangGraph batch (2026-07-11)

- **The non-negotiable harness boundary: runtimes (LangGraph today, OpenCode later) may only act through `HarnessCapabilityExecutor.execute()` — never give a graph node, planner, or runtime adapter a direct provider handle.** The executor is the single place where permissions, risk tiers/approvals, JSON-schema input types, and project scope are validated and where observations are sanitized. `test_runtime_provider.py` pins this; any new graph node that imports a provider directly is a regression even if tests still pass.
- **`LangGraphRuntimeProvider()` is currently constructed per request (`chat.py:734`), so every request gets a fresh `InMemorySaver` and every persisted `resume_token` is unredeemable — even without a backend restart.** `runtime_metadata.resume.ready=true` on interrupted runs is a forward promise, not a capability. Slice 6 must introduce a shared (min. process-lifetime, preferably Postgres-backed) checkpointer AND a resume endpoint; fixing only one of the two still leaves resume broken.
- **Interrupted scope-clarification runs store the sentinel `project_id="__pending_project_scope__"`, which is invisible to its own creator through `/harness/workflows`** — project-scoped RBAC filters `project_id IN (user scope)` and the sentinel never matches. Resume/interrupted-run lookup must key on `conversation_id` + `user_id`, not project scope. There is deliberately no test asserting owner retrieval of an interrupted run yet (it would fail today); add it with Slice 6.
- **Graph timeout vs. provider side effects: `asyncio.wait_for` around `graph.ainvoke` can cancel AFTER the MCP `/generate` POST committed**, marking the workflow run `failed` while a real generation runs on MCP (user retry then duplicates work). Timeout handling for any capability with side effects must reconcile against the provider's run status before finalizing the receipt — do not copy the current pattern for new write-capable capabilities.
- **The MCP docs provider (`providers/mcp_docs.py`) does not validate `project_id`/`filename` path segments; safety currently depends on the caller's `_DOC_FILENAME_RE` regex in `chat.py`.** This is acceptable ONLY while all arguments are regex-extracted. Before the model-backed planner (or any model) supplies capability arguments, path-segment validation must move into the provider/executor boundary.
- **Two orchestration paths coexist: only docs generation goes through LangGraph; investigation/connector-inventory/doc-update still use the direct path in `chat.py`, and `executor._dispatch` supports exactly one capability id.** Rule until consolidation: no new capability lands on the legacy direct path, and every new executor-dispatchable capability extends `_dispatch` (or its future registry), not `chat.py` branching.
- **Backend test invocation: plain `uv run pytest` fails with "Failed to spawn: pytest" — pytest lives in the `dev` extra.** Use `uv run --extra dev pytest`.

### Nexus harness Slices 6-9 invariants (2026-07-11)

- **Supersedes the stale Slice 6 warnings above:** workflow interrupts are durable,
  owner-bound, expiring, optimistic-versioned, single-use, cancellable, and resumable.
  Nexus records allow reconstruction when the process-lifetime LangGraph saver is empty.
- **Model tool names are transport details, never capability IDs.** Internal capability IDs
  may contain dots; providers receive stable `nexus_tool_<sha256-prefix>` names. Native tool
  calls and validated JSON plans map back before manifest/schema/policy validation.
- **Never pass empty chat history to a model provider.** Failed assistant messages can have
  empty content; the planner boundary must omit them.
- **Onboarding order is strict:** attach source -> trigger scan -> bounded poll until
  `ready|completed` -> generate docs -> publish only if docs already exist, otherwise persist
  index pending. Triggering docs directly after `/scan` reproduces a real missing-scan-output
  failure.
- **Dynamic connector tools are request-scoped projections.** Manifest filtering is not
  enough: execution must re-read enabled/health/binding/project/domain state so a stale tool
  selection cannot run after revocation.
- **Evidence cited in answers must be persisted and marked used.** Conflicting claims are
  retained under a conflict group and the answer must disclose disagreement.
- **Do not serialize workflow `input_summary`, interrupt policy/scope snapshots, argument
  hashes, response summaries, or credential references.** User evidence and approval payloads
  belong in excluded internal state, not public receipts.

### Nexus harness Slices 10-13 invariants (2026-07-12)

- **Published documents are not a workflow-status authority.** Documentation completion, failure, quality, and client readiness must come from the generation-run ledger; file lists only describe artifacts.
- **Time constraints are enforced after model planning.** A model-selected runtime capability must receive the deterministically resolved `since`/`until` bounds even when its proposed arguments omit them. Runtime observations outside the half-open UTC window are discarded.
- **A complete operational investigation requires docs, runtime, and connector/log evidence plus a supported synthesis.** Missing required source classes produce a qualified, semantically unsuccessful result; never hide the gap behind a confident prose answer.
- **Document approval binds content identity.** Every proposed update carries the current base SHA, publish uses that SHA as a precondition, indexing failure restores the previous file, and revert accepts only the matching receipt/version. MCP document reads may be raw Markdown or JSON and adapters must support both.
- **Packs are executable policy, not prompt decoration.** The active Pack include closure compiles both the model-visible manifest and executor registry. A disabled capability must be impossible to execute even if a model names it. Snapshot active Pack IDs and hashes on every workflow run.
- **Workflow metadata updates merge rather than replace.** Resolution, exact time window, evidence state, and Pack snapshot must survive subsequent status/receipt updates.
- **User-facing synthesis never exposes internal capability IDs, raw provider payloads, document byte dumps, or hidden chain of thought.** The activity timeline may show safe action summaries, evidence sources, status, artifacts, and recoverable errors.

### Agentic runtime orchestration invariants (2026-07-14)

- **A runtime TurnPlan is an execution obligation, not optional context for the legacy RAG path.** Once the harness selects `runtime_answer`, execute the runtime capability through `HarnessCapabilityExecutor`; do not hand the same turn to a second router that may answer from documentation or prose alone.
- **Runtime entities and Nexus project scope are different dimensions.** Engine/job/source names such as `ESB_PROD` stay in the capability question. Only an actual accessible Nexus project ID may populate `project_id`.
- **Clarification must preserve typed task state durably.** Store objective, task type, entity, project, time window, evidence policy, missing slots, and version in the owner-bound conversation continuation row. A short slot answer such as `cdc` or `last 2 days` supplements that envelope; it never becomes the new objective.
- **Evidence-only policy is enforced during execution.** A runtime-only request must not retrieve indexed/generated documentation as a fallback. Missing runtime evidence yields an insufficient answer, not a fabricated capability denial or a documentation answer.
- **Executor success follows the handler receipt.** A failed `EvidenceQueryResult` is a failed observation even if the transport call returned normally. Deduplicate evidence identities before persistence and never mark duplicate IDs as used.
- **The runtime evidence capability delegates to the bounded LLM runtime tool loop.** Do not regress it to a fixed list of three tools. Persist sanitized receipts and a bounded evidence summary, while retaining the complete user-facing answer separately for synthesis/replay.
- **Recomposition is read-only replay.** Requests such as "show me the results" reuse the prior workflow ID and the most complete persisted assistant answer. They must not create a new workflow, invoke runtime tools, or overwrite a detailed answer with a generic evidence placeholder.

### Consolidated Nexus harness foundation invariants (2026-07-14)

- **Runtime scope is typed, not inferred from a nullable string.** Preserve `global`, `single_project`, and `multi_project` semantics through planning, continuation, execution, receipts, and RBAC. Do not force global inventory questions into an arbitrary project.
- **Durable checkpoints contain sanitized orchestration state only.** Never persist credentials, ZIP bytes, authorization headers, raw provider payloads, or hidden reasoning. Secure uploads cross the graph boundary through short-lived opaque receipts and safe metadata.
- **Automatic workflow reconciliation is credential-gated and bounded.** It is disabled when `MCP_DOCS_RECONCILIATION_SERVICE_TOKEN` is absent, uses a least-privilege service identity, limits each polling batch, and retains the credential in process memory only.
- **Connector registration is declarative; execution remains guarded.** Provider configuration projects capabilities into the request-scoped registry, but the executor must revalidate enabled state, health, project binding, schema, permissions, and risk before every call.
- **Nexus policy Packs and IntoDoc swap packs are distinct but connected.** Nexus Packs compile application capabilities/policy. IntoDoc swap packs define the generated documentation set and prompts. Project selection of an IntoDoc pack persists as MCP `plugin_pack_id`; explicit per-run overrides win, otherwise generation uses the project default.
- **Slash commands are discoverability and scoping hints, not a second intent router.** Commands feed the same planner, capability manifest, policy, continuation, and executor path as natural language.
- **User-visible activity is a safe execution trace, not chain of thought.** Show bounded actions, source classes, progress, artifacts, clarification, errors, resume, and cancel; never expose internal capability IDs, raw tool payloads, secrets, or private model reasoning.

### Documentation Pack builder invariants (2026-07-17)

- **"Pack" is a user-facing documentation/Swap Pack term.** Do not list internal capability-policy fixtures such as `nexus.documentation` or `nexus.data-integration` as user-selectable documentation Packs. Internal capability policy may remain an implementation detail, but `/pack`, Pack inventory, onboarding, and `/docs` must speak only about what IntoDoc analyses and generates.
- **Private Pack drafting is project-independent.** A user creates and versions a reusable private Pack before choosing any project. Project binding happens at preview/activation/generation time, not draft creation time. Drafts are owner-bound; `conversation_id` is optional and must never be required by the workbench.
- **Workbench LLM actions are in-place operations.** New, Edit, Refine, attach, preview, and save use dedicated Pack builder endpoints and must not create, replace, or navigate to chat threads. `/pack create` may use the same guarded builder from chat, but the side panel remains an independent workspace.
- **Model Pack proposals are untrusted complete artifacts.** Parse them through `PackArtifactV3`, reject protected/executable fields, enforce revision ownership, and persist only after validation. A vague request such as "create a Pack" must ask for purpose, outputs, and audience instead of inventing a generic Pack.
- **Reference files need an explicit purpose and bounded extraction.** Accept only formats the backend can actually extract; store filename, content type, byte size, SHA-256, purpose, and bounded text. Current limits are 10 MB per file, 20 references per Pack, 12k extracted characters per reference, and 32k aggregate characters supplied to one builder turn. Do not enable images until OCR/vision produces usable evidence.
- **Upload completes before model mutation.** For prompt-plus-file and file-only turns, upload references first and then call assist. Show file progress separately from model progress, remove each queued item only after its upload succeeds, and retain failed/unattempted items for retry.
- **Certified semantics outrank private additions.** Foundation/Core and certified Functional rules are immutable and Git/PR governed. User/private artifacts may deepen analysis, define outputs/audience/style, and add reference context, but cannot weaken evidence, permissions, safety, required content, provider identity, or organization policy.

### Unified agentic chatbot invariants (2026-07-19)

- **One public chat path.** Both conversation transports call the same bounded agent service exactly once; SSE is a projection of the completed typed result and never reruns or redispatches the turn.
- **The LLM chooses intent; deterministic authorities constrain execution.** The model may answer, clarify, or request a manifest capability. Registry definitions, policy, RBAC, schema validation, risk/approval gates, project scope, budgets, Conversation State, Workflow Ledger, and evidence provenance remain server-owned.
- **CapabilityCatalog is non-executable.** `CapabilityRegistry` binds exactly one schema/output/task-compatible handler to every executable definition. There is no `MANIFEST_ONLY`, legacy dispatch, capability-ID switch, nested runtime umbrella, or generic connector executor fallback.
- **RAG is a capability, not a chat router.** Explicit `/query` remains a deterministic retrieval API; it has no intent classifier. Conversation RAG, keyword Pack gates, old planners, and frontend workspace/event guesses cannot select execution.
- **Typed response authority.** `agent_response` is the only visible SSE answer. `agent_final` carries terminal metadata only. Persisted typed responses, history, workflow cards, non-streaming, and streaming must remain equivalent.
- **Retirement migration is fail-closed.** Migration 069 may drop legacy continuation storage only after Conversation State parity and any explicitly referenced task/workflow/draft authority are verified. It is unapplied in this worktree.
- **Deployment gate is separate from implementation.** Offline tests do not satisfy the required deployed Slice 7 observation window: at least 168 consecutive hours and 1,000 authenticated full-agent turns with reviewed thresholds, backup, and rollback evidence.

### Conversational action recovery invariants (2026-07-22)

- **Proposal correction is not capability retry.** One correction may repair an invalid model proposal only before a handler executes. Once any consequential handler is attempted, the same-turn retry prohibition remains absolute.
- **Prepared action state is context, never authority.** Persist it only for capabilities that explicitly opt in; bound its size and source-message history; version it with Conversation State; and require a fresh exact assessment, RBAC/policy/schema validation, and turn claim before execution on every later turn.
- **Ask users for domain facts, not runtime internals.** The model owns the single clarification question. Never expose capability IDs, evidence IDs, payload/schema fields, or narration about fixing/retrying a tool proposal.
- **Successful matching execution consumes preparation.** A completed consequential action must clear the corresponding prepared state so a later conversational turn cannot accidentally revive it.

### Atomic conversational Pack creation invariants (2026-07-22)

- **Chat exposes a usable-Pack action, not a draft primitive.** `create_pack` is model-visible; `create_pack_draft` is internal-only for explicit Workbench flows and must not appear in the semantic tool snapshot.
- **Readiness precedes persistence.** Conversational Pack creation requires name, purpose, audience, focus/goals, and at least one output document. Missing facts produce a clarification and zero Pack/draft/version rows. Optional fields such as `required_domains` must not block creation.
- **Creation is atomic and produces a usable version.** Translate friendly input deterministically, validate the complete `PackArtifactV3`, then create the audit draft and immutable private version in one transaction. Any receipt, validation, or persistence failure rolls back all Pack artifacts.
- **No active placeholder survives success.** The internal audit draft must contain the validated artifact and immediately end in `saved`; successful chat creation must not leave an active `{}` draft or an active Pack task reference.

### Generic clarification grounding invariants (2026-07-22)

- **Clarification is untrusted model output, not authority.** A schema-valid string is insufficient. Before display, normalize it and compare it with every current/recent user message available to the turn; exact and near copies are invalid.
- **Direction must be explicit.** Assessment contracts use `clarification_to_user`, never ambiguous `user_question`. A prepared action requires exactly one direct question, human-facing missing information, and the exact partial semantic tool proposal.
- **Preparation preserves recognized work.** The model may not select `prepare` while discarding the chosen tool and known arguments. Only capabilities that opt into prepared-action persistence store the partial proposal; persistence still grants no execution or approval authority.
- **Correction is bounded and pre-execution.** One malformed-assessment correction is allowed before any capability handler runs. If the provider skips or fails correction, show a capability-agnostic non-echo fallback instead of raw model prose.
- **Shared clarification code is domain-blind.** It may use structured assessment data, tool schemas, normalized message fingerprints, and bounded human-facing missing descriptions. It must never branch on Pack/onboarding/documentation capability IDs, project names, keywords, or domain phrases.

A successful, non-empty answer with document sources is a terminal trusted result; the outer conversational agent must not ask another model to paraphrase it.

- **Do not confuse orientation with ingestion.** “Brief me,” “orient me,” or “onboard me” about an existing project is documentation Q&A. Source onboarding is only for adding or indexing a new Git/ZIP/project source.

### Direct Pack Architect invariant (2026-08-24, supersedes Pack-specific OpenCode)

- **Pack authoring is one direct design call, not an OpenCode or repair loop.** Persist the user turn before dispatch; model output is a compact complete design or one clarification question. MCP renders canonical files deterministically and validates them atomically.
- **Interactive does not mean a long-lived HTTP request.** POST returns an accepted running snapshot; clients poll the owner-scoped session, may cancel, and recover the latest active draft after refresh or service restart.
- **Recovery is explicit at the New-pack boundary.** Detect an active browser/server draft, but do not automatically replace the clean creation form with it. Offer **Resume previous draft** and restore identity only after the user chooses it.
- **AI refinement preserves Pack identity.** Seed the Architect from the complete owned Pack, bind the session to its source Pack ID, and save back atomically with Git history. Never create a duplicate or disturb project selections; never permit this path for another user's or a shared Pack.
- **One Plugin Pack identity crosses every surface.** Workbench, chat compatibility, port 8001 document generation, project defaults, and explicit generation requests use the MCP Plugin Pack registry and one `plugin_pack_id`. Do not revive the deleted RAG workspace route or parallel governed/style Pack tables.
- **Breadth follows user intent.** The schema has no product-level document/file/section count ceiling. Technical artifact-size and path-safety limits remain implementation safeguards, and users may extend the design through later turns.
- **Runtime trend absence is unknown unless capture completeness is known.** The aggregate API omits empty buckets, but a missing bucket can be an ingestion/backfill gap rather than zero source executions. UI adapters may preserve the time position, but must say “no captured records” and must not infer downtime. A future “zero runs” claim requires persisted source coverage windows.
- **Duration-scale decisions compare like with like.** Keep raw millisecond percentiles in API data, tooltips, and tables. Detect temporal outliers within p50 and p95 separately; never trigger logarithmic presentation merely because p95 is naturally much larger than p50. Never silently clip genuine multi-day observations.
