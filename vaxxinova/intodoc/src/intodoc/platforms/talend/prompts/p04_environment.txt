You are analyzing a Talend integration project. Your task is to produce an **Environment & Configuration Analysis** — a comprehensive comparison of context variables across environments, identification of risky differences, missing values, and hardcoded production credentials or endpoints.

## Talend Context
In Talend, environment-specific configuration is managed through **context variables** and **context groups**:
- **Context variables**: Named parameters (e.g., `db_host`, `db_port`, `db_password`) that hold environment-specific values. They are defined at the job level or globally and can be overridden at runtime.
- **Context groups**: Named environments such as "Default", "PROD", "TEST", "DEV", "UAT". Each group provides a different set of values for the same context variables. When a job runs, one context group is active.
- **Default context**: The fallback context group. If no environment is specified at runtime, Default values are used. This is risky if Default contains production values.
- **Context load mechanisms**: Jobs can load context values from files (tContextLoad), databases, or command-line parameters at runtime, overriding the built-in values.
- **Implicit contexts**: Talend Studio can configure "implicit context load" at the project level, automatically loading context from a database table on every job run.
- **Repository context groups**: Context groups defined once in the repository and shared across multiple jobs, versus job-specific context groups defined inline.
- **Password fields**: Context variables of type "Password" are stored encrypted in the .item files but may appear as plaintext in exported archives or properties files.
- **Built-in vs Repository**: Components can use BUILT_IN settings (hardcoded in the job) or REPOSITORY references (pointing to shared metadata). BUILT_IN settings are a maintenance risk as they must be updated in every job individually.

## What to Extract

1. **Context variable inventory**: For each job, list every context variable with its name, type (String, Integer, Password, etc.), and value in each context group (Default, PROD, TEST, etc.).

2. **Cross-environment comparison**: For each context variable, compare values across all context groups. Flag:
   - **Identical values across PROD and TEST**: This suggests the TEST environment may point to production systems (HIGH RISK)
   - **Missing values**: Variables defined but with empty or null values in certain environments
   - **Default = PROD**: Default context group containing production values (RISK: accidental production execution during development)
   - **Hardcoded production URLs/IPs**: Production server addresses, database hosts, or API endpoints embedded directly in component configurations (not via context variables)

3. **Password and credential analysis**:
   - Identify all Password-type context variables
   - Flag any credentials that appear to be in plaintext
   - Identify any hardcoded credentials in component BUILT_IN configurations
   - Note which jobs handle sensitive credentials

4. **Context loading patterns**:
   - Which jobs use tContextLoad to dynamically load configuration?
   - What is the source of dynamically loaded context (file, database, API)?
   - Are there jobs that do NOT load context dynamically but should (because they use many context variables)?

5. **BUILT_IN vs REPOSITORY usage**:
   - For each component using connection parameters, is it BUILT_IN (hardcoded) or REPOSITORY (shared metadata)?
   - Flag BUILT_IN database connections as a maintenance risk
   - Identify inconsistencies where some components in a job use REPOSITORY and others use BUILT_IN

6. **Environment isolation risks**:
   - Can a TEST run accidentally write to PROD tables based on the context configuration?
   - Are there any context variables where the PROD and TEST values point to the same server/database?
   - Are there file paths that are environment-specific but hardcoded?
