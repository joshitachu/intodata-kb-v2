You are analyzing a Talend integration project. Your task is to produce a **Reusability & Refactoring Analysis** — identify duplicated logic, opportunities to extract shared components (routines, joblets, metadata), code smells, unused assets, and create a refactoring roadmap to improve maintainability and reduce technical debt.

## Talend Context
Talend projects often accumulate technical debt as they grow:
- **Duplicated tMap expressions**: The same transformation logic (TRIM, UPCASE, date formatting, null handling) repeated across multiple jobs. This violates DRY (Don't Repeat Yourself) and makes maintenance harder — if the logic changes, you must update it in many places.
- **Similar job structures**: Regional jobs (BRA_VBR_RAW, ITA_VAX_RAW, etc.) often have nearly identical structure with only connection names and table names different. These could be replaced with a single parameterized job.
- **Joblets**: Reusable components that encapsulate a set of components into a single unit. If you see the same component pattern repeated (e.g., tJava -> tMap -> tBigQueryOutput), that's a joblet candidate.
- **Routines**: Shared Java code libraries. Common use cases:
  - Data validation: `Routines.DataValidation.isValidEmail(String)`
  - Data cleansing: `Routines.DataCleansing.cleanPhoneNumber(String)`, `Routines.DataCleansing.trimAndUppercase(String)`
  - Data masking: `Routines.DataMasking.maskSSN(String)`
  - Calculation formulas: `Routines.BusinessLogic.calculateDiscountedPrice(BigDecimal, BigDecimal)`
  - Date utilities: `Routines.DateUtils.getFirstDayOfMonth(Date)`, `Routines.DateUtils.isWeekend(Date)`
- **Metadata**: Reusable connection definitions, file schemas, database schemas. REPOSITORY mode centralizes metadata — components reference it instead of duplicating definitions (BUILT_IN mode).
- **Context variables**: Parameterize jobs to make them reusable across environments (PROD, TEST) or regions (BRA, ITA, etc.).
- **Code smells**: Anti-patterns that indicate poor design:
  - Magic numbers/strings: hardcoded values like "A" for Active, "2020-01-01" for cutoff date — should be context variables or constants
  - God jobs: jobs with 50+ components doing too many things — should be split
  - Copy-paste code: exact duplicates of component configurations or tMap expressions across jobs
  - Unused components: components with no connections (orphans) or test/debug components left in production code
  - Dead code: jobs or routines that are never called
  - Inconsistent naming: mix of naming conventions within a single project

## What to Extract

1. **Duplicated tMap expressions**: For every tMap expression that appears in multiple jobs:
   - Expression text
   - What it does (plain English)
   - Where it appears (job names, component names)
   - How many times it's duplicated
   - Recommended refactoring (extract to routine, parameterize, etc.)

2. **Duplicated job structures**: Identify sets of jobs with similar structure:
   - Pattern description (what the jobs do)
   - Jobs that follow this pattern
   - What varies between them (connection names, table names, parameters)
   - Recommended refactoring (parameterized job, joblet, etc.)

3. **Joblet candidates**: Identify component patterns that are repeated and could be extracted into joblets:
   - Component sequence (e.g., tFileExist -> tJava -> tLogRow)
   - Where this pattern appears
   - What the pattern does
   - How much duplication would be eliminated

4. **Routine candidates**: Identify Java code that should be extracted into routines:
   - Code snippet
   - Where it appears (tJava, tJavaRow, tMap expressions)
   - What it does
   - How many times it's duplicated
   - Proposed routine signature (e.g., `Routines.DataCleansing.cleanCustomerName(String name)`)

5. **Shared components usage**: For existing routines and joblets:
   - Which routines/joblets exist?
   - How often are they used?
   - Are there routines that are defined but never used (dead code)?
   - Are there opportunities to use existing routines instead of duplicating logic?

6. **Metadata centralization**: For connections and schemas:
   - What % of components use REPOSITORY metadata vs BUILT_IN?
   - Are there duplicate connection definitions (same database, different .item files)?
   - Are there duplicate schema definitions?

7. **Code smells**: Identify anti-patterns:
   - Hardcoded values that should be parameterized
   - Jobs that are too large (>30-50 components)
   - Orphaned components (no connections)
   - Unused jobs (never called by tRunJob or scheduler)
   - Inconsistent naming (jobs that don't follow the standard pattern)
   - Magic numbers and strings

8. **Reusability score**: Rate the project's reusability (1-10) based on:
   - Routine usage (are common operations in routines or duplicated in jobs?)
   - Joblet usage (are repeated patterns extracted?)
   - Metadata centralization (REPOSITORY vs BUILT_IN)
   - Code duplication level

9. **Refactoring roadmap**: Prioritized list of refactoring opportunities:
   - What to refactor
   - Why (benefit)
   - Effort (low, medium, high)
   - Priority (critical, high, medium, low)
   - Risk (low, medium, high — could refactoring break something?)
