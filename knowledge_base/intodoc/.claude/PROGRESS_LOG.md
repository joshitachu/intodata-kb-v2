## Session: 2026-09-09 -- Linear credential-path redaction (UNCOMMITTED)

- **Files changed**: `src/intodoc/scanner/credential_filter.py`; `tests/test_scanner/test_credential_filter.py`.
- **Problem**: the next real scan (`ETTM_ZIP_TEST`, same 7,295-file estate) parsed fine in 12.6s and then appeared to hang. The process was alive, State `R`, burning a full CPU with no file descriptor open, 155 CPU-seconds spent and only 178 of 6,795 sanitized files written after several minutes.
- **Root cause**: the credential-path pattern `[^\s"'<>]*(Credentials|gcp\.json|service_account|\.pem|\.key)[^\s"'<>]*` has two unbounded runs around an alternation and no anchor, so it is retried at every position inside every delimiter-free token: quadratic in token length. Measured on this estate, one 16 KB metadata XML cost 1.08s for ZERO matches and `maximo_po_0.1.item` cost 60.3s on its own. The pattern is pre-existing, but this session's `write_sanitized_workspace` is what made it fatal: `filter_text` previously ran only on the files the parser actually read, and now runs on every textual file, with `detect_residual` running the same pattern set twice more for XML. One pass over the 6,768-file corpus spent 89.6s in this single pattern.
- **Change**: anchored the pattern to the start of a delimiter-free token with `(?<![^\s"'<>])`. At a position inside a token the lookbehind now fails immediately instead of re-running both unbounded quantifiers, which takes the whole pattern from quadratic to linear. The reasoning and the measured numbers are recorded beside the pattern, because it reads like a style detail and is load-bearing for performance.
- **Why this approach**: fixing the regex fixes both consumers (`filter_text` and `detect`) at once and preserves behaviour exactly, which a narrower change (skipping large files, capping the token length, or excluding `metadata/` from the mirror) would not: each of those would have withheld real evidence to hide a quadratic regex. Equivalence was verified rather than assumed.
- **Verification**: ran both patterns over all 6,768 textual files of the real estate: byte-identical `sub` output on every file, `89.56s -> 1.62s` (55x), worst single file `60.3s -> under 20ms`. After the fix no pattern in the active set exceeds 20ms on the worst file, and its full pipeline is `filter_text` 0.025s plus `detect_residual` 0.074s. Full suite `665 passed, 7 skipped`; `ruff check src tests` clean. New tests pin the complexity (a 40,000-character marker-free token must filter in under a second), that a marker inside a long token still redacts the whole token, and that markers are still caught at a token start after any delimiter. Rebuilt the container and reran the scan end to end: **65s wall clock**, all artifacts written including `scan_result.json` and `publication_approval.json`, 142 designs, 6,795 sanitized files with 624 benign exclusions. The enterprise stager then consumed it: 142 of 142 designs with a readable sanitized file each, 77 mapping tables, 275 resolved edges.
- **Correction to the previous entry**: it reported the earlier `ETTM_ZIP` scan as completing "in 17.0s". That figure is the parse time the tool prints, not the wall clock, and that run silently paid the same quadratic cost during its sanitized-workspace write. Timed end to end, that run would have taken minutes.

## Session: 2026-09-09 -- Resilient, case-exact filesystem traversal (UNCOMMITTED)

- **Files changed**: new `src/intodoc/scanner/fswalk.py`; `src/intodoc/scanner/walker.py`; `src/intodoc/platforms/base_parser.py`; `src/intodoc/platforms/talend/{parser,xslt,structures,services}.py`; `src/intodoc/platforms/lobster/parser.py`; `src/intodoc/platforms/workato/parser.py`; new `tests/test_scanner/test_fswalk.py`.
- **Problem**: the first real customer scan after the enterprise work (`ETTM_ZIP`, 7,295 files) died with `FileNotFoundError: [Errno 2] .../WorkOrderData/Process` raised out of `Path.rglob` in the new XSLT discovery pass. Exit code 1, no scan output at all.
- **Root cause**: two independent defects. (1) `Path.rglob` has no error hook in 3.11, so a single `OSError` below the root propagates out of the generator and aborts the whole scan; `/app/data` is a Docker Desktop macOS bind mount (`type fakeowner`) that intermittently returns ENOENT for a directory which `stat`, `listdir` and `scandir` all resolve correctly moments later (reproduced twice, clean pass twice, same process and path). Every walk site in the scanner had the same exposure -- roughly twenty `rglob`/`glob`/`iterdir` calls including `walk_repo` and Talend item discovery -- so any permission-denied or concurrently-removed directory would kill a scan the same way. (2) That mount is case-insensitive, so `(candidate / "process").is_dir()` was true for a customer data folder named `Process`, and `.../Maximo2Assetcheck/WorkOrderData` (holding `Process/Processed`) was registered as a Talend execution root and then walked as though it held Job Designs. That is why the fragile walk was pointed at that subtree at all.
- **Change**: new `scanner/fswalk.py` owns both rules. `walk_files` / `walk_dirs` / `child_dirs` walk with an explicit `on_error` hook, retrying a failing directory once (a transient bind-mount ENOENT succeeds on the second call, and recovering real evidence beats warning about evidence that is present) and then reporting it and continuing. `child_dir` / `child_file` / `case_variant_names` compare against the real name from `scandir`, so platform-convention directories match exactly. Every scanner walk now uses them: `walk_repo` (which also records an `excluded` inventory row for the unreadable directory), Talend root/descriptor discovery, versioned item discovery (now one walk feeding both passes, which also stops the two passes disagreeing), job-id index, contexts, routines, metadata connections, Maps, unscanned-category counting, Structures, XSLT, services, plus the Lobster and Workato walks. `BaseParser._walk_error` records an `unreadable_directory` warning through one shared message factory, and `_warn_case_variant` records a `case_variant_directory` warning so a differently-cased directory is a named skip rather than a silent one.
- **Why this approach**: a directory walk is discovery, and the scanner's contract is that unsupported or unreadable material becomes an explicit warning, never a dead scan. Fixing only the XSLT call site would have left nineteen identical traps. The bounded single retry is I/O robustness with a named failure, not a suppressed error. Case-exact matching is strictly more correct: Talend's repository layout has fixed casing, and the alternative silently mis-classifies customer folders on every macOS and Windows mount.
- **Verification**: `.venv/bin/python -m pytest -q tests` -> `662 passed, 7 skipped`; `ruff check src tests` -> `All checks passed!`. New tests cover a persistently unreadable directory (walk continues, one retry, warning emitted), a transient failure (retry recovers, no warning), case-exact root and support-project detection, a full scan surviving an unreadable subtree, and a case-variant directory being warned. One test had to be split because creating `code/routines` beside `Code/Routines` is refused on this filesystem -- the same property that caused the bug. Rebuilt the container and re-ran the exact failing scan: completes in 17.0s, 142 designs (71 jobs, 44 routes, 22 joblets, 5 routelets), 1,396 indexed files, roots now `ETTM-2/ERP_TO_THE_MAX` and `ETTM-2/REFERENCES` with the bogus `WorkOrderData` root gone, 173 route-to-job invocations, sanitized workspace 6,795 files with 624 exclusions that are all hidden paths or non-textual extensions and zero residual-secret withholdings. The enterprise stager then consumed that scan: all 142 designs present with a resolvable sanitized design file each, 275 resolved dependency edges and no unresolved ones, 77 mapping tables holding 530 exact rows, both nested-zip subtrees mirrored. NOTE: this run proves the case fix removed the trigger; the resilience fix is proved by its unit tests, not by this run, because the mount did not hiccup this time.
