You are analyzing a Workato integration project. Your task is to produce a **State & Side Effects Analysis** -- a thorough identification of every persistent state store, runtime mutation, external side effect, and cleanup gap in the recipes in this chunk, with an assessment of idempotency and re-run safety.

## Workato Context
Workato recipes produce state and side effects that persist beyond the recipe run:

- **Workato DB tables**: Built-in database tables used for persistent state -- tracking processed record IDs, storing intermediate results, audit logs, deduplication keys, and watermark values (e.g., `last_sync_timestamp`). Actions: `workato_db_query`, `workato_db_insert`, `workato_db_update`, `workato_db_delete`. In the scan data these appear as `WorkatoAction_workato_db_*` component types. Workato DB has row limits per plan -- unbounded inserts without cleanup will hit plan limits.

- **Lookup tables**: Reference data tables that can be mutated at runtime via `add_lookup_entry` / `update_lookup_entry` / `delete_lookup_entry` actions. When used for read-only reference data (code mappings, config values), they are safe. When mutated at runtime (tracking state, counters, flags), they become stateful and order-dependent. In scan data: `WorkatoAction_lookup_table_entry` (read), `WorkatoAction_add_lookup_entry` (write).

- **Properties**: Account-level (`account_property`) or project-level (`project_property`) configuration variables. These are typically read-only during recipe execution but can be updated programmatically. Properties persist across recipe runs and environments (DEV/PROD). In scan data, property references appear in datapill expressions.

- **Event topic publishing**: `publish_event` actions send asynchronous events to named topics, triggering downstream subscriber recipes. This is a fire-and-forget side effect -- the publisher does not know if subscribers succeed or fail. In scan data: `WorkatoAction_publish_event`.

- **External system state changes**: Actions that create, update, delete, or upsert records in external systems (Salesforce, NetSuite, databases, etc.) produce persistent side effects. These include `create_record`, `update_record`, `upsert_record`, `delete_record`, `run_sql`, `send_request` (POST/PUT/DELETE). These are the most impactful side effects -- they change data in production systems.

- **File operations**: `upload_file` and `download_file` actions create or retrieve files in cloud storage (S3, SFTP, Google Drive). Uploaded files persist until explicitly deleted.

- **Notification side effects**: `send_email`, `send_message` (Slack/Teams) actions produce irreversible side effects -- messages cannot be unsent.

- **No automatic cleanup**: Unlike platforms with post-execution hooks, Workato has no built-in `tPostJob` equivalent. There is no automatic cleanup phase. State persists until explicitly purged by a separate recipe or manual action.

## What to Extract

1. **Workato DB state**: For each recipe, identify:
   - Every Workato DB read/write operation (query, insert, update, delete)
   - Table name and purpose (tracking, staging, audit, dedup)
   - Whether rows are cleaned up after use or accumulate indefinitely
   - Row growth rate estimate (inserts per run, per day)
   - Risk of hitting plan row limits

2. **Lookup table mutations**: For each recipe:
   - Which lookup tables are read (reference data usage)
   - Which lookup tables are written to at runtime (state mutation)
   - Whether runtime mutations could cause race conditions if multiple recipe runs overlap
   - Whether lookup table data is ever purged or archived

3. **Properties as config state**: Identify:
   - Which properties are referenced (account_property, project_property)
   - Whether any recipes update properties at runtime
   - Whether property values are environment-specific (DEV/PROD differences)

4. **Event topic side effects**: For each `publish_event` action:
   - Topic name and payload schema
   - Which downstream recipes subscribe
   - Whether subscriber failure could cause data inconsistency
   - Whether there is dead-letter handling for failed subscribers

5. **External system state changes**: For each recipe, catalog every action that modifies external data:
   - Target system and operation (create, update, upsert, delete, run_sql)
   - Whether the operation is idempotent (upsert = yes, insert = no)
   - Whether the operation is reversible
   - What happens if the recipe fails mid-execution (partial writes)

6. **Cross-recipe state sharing**: Identify recipes that share state via:
   - Shared Workato DB tables (producer/consumer pattern)
   - Shared lookup tables (one recipe writes, another reads)
   - Shared external tables or staging areas
   - Event topics (pub/sub state transfer)

7. **Idempotency assessment**: For each recipe, assess re-run safety:
   - Can the recipe be safely re-run without creating duplicate data?
   - Does it use upsert (idempotent) or insert (not idempotent)?
   - Are there dedup keys on triggers (`updated_at` sorted columns)?
   - Would a re-run send duplicate notifications?
   - Would a re-run publish duplicate events?

8. **Cleanup gaps**: Identify state that persists but is never purged:
   - Workato DB rows that grow without bounds
   - Lookup table entries that accumulate without archival
   - External staging tables never truncated
   - Files uploaded but never deleted
