You are analyzing a Workato integration project. Your task is to produce a **Naming Conventions Analysis** -- decode and document the naming patterns used for recipes, folders, connections, event topics, properties, lookup tables, and custom adapters.

## Workato Context
Naming conventions in Workato integration projects serve as embedded documentation. Consistent naming makes the project self-documenting and reveals organizational structure, integration purpose, and environment targeting:

- **Recipe naming**: Recipes are typically named to describe their purpose. Common patterns include:
  - `{Source} to {Target} - {Action} {Object}` (e.g., "Salesforce to NetSuite - Sync Customers")
  - `{Trigger Type} - {Purpose}` (e.g., "Scheduled - Daily Sales Report to BigQuery")
  - `API - {Endpoint Name}` (e.g., "API - Create Customer Endpoint")
  - `Webhook - {Purpose}` (e.g., "Webhook - Process Incoming Order")
  - Some projects use prefixes, codes, or numbering systems

- **Folder organization**: Recipes are organized in folders that map to the project's `group` field in the scan data. Folder structures reveal organizational patterns:
  - By department: `/Sales/`, `/Finance/`, `/Operations/`
  - By integration: `/Salesforce Sync/`, `/NetSuite Integration/`
  - By function: `/Main/`, `/Workers/`, `/Error Handling/`, `/Utilities/`
  - Flat: All recipes in root folder (anti-pattern at scale)

- **Connection naming**: Connections identify external system access points. Common patterns:
  - `{App} - {Environment}` (e.g., "Salesforce - Production")
  - `{App} - {Environment} ({Purpose})` (e.g., "PostgreSQL - Staging (Data Warehouse)")
  - `{App}_{environment}` (e.g., "salesforce_prod")
  - Provider-only names (e.g., "salesforce") -- risky because they hide environment context

- **Event topic naming**: Topics connect publishers and subscribers. Patterns include:
  - `{domain}.{event_type}` (e.g., "orders.new_order", "customers.updated")
  - `{action}_{object}` (e.g., "new_order", "customer_updated")
  - Descriptive names (e.g., "New Order for Fulfillment")

- **Property naming**: Account-level and project-level properties parameterize recipes. Patterns include:
  - `{scope}_{parameter}` (e.g., "prod_api_url", "staging_api_key")
  - `{system}_{parameter}` (e.g., "erp_base_url", "crm_api_version")
  - `{snake_case}` vs `{camelCase}` vs `{UPPER_CASE}` conventions

- **Lookup table naming**: Reference data tables. Patterns include:
  - `{purpose}_mapping` (e.g., "country_code_mapping", "status_translation")
  - `{domain}_{object}` (e.g., "sales_regions", "product_categories")

- **Custom adapter naming**: Custom connectors. Typically named after the target system:
  - `{system_name}_connector` or `{system_name}_adapter`
  - `custom_{system}` or `{vendor}_{product}`

## What to Extract

1. **Detected naming patterns**: For each category (recipes, folders, connections, topics, properties, lookup tables, adapters), identify:
   - The naming pattern template
   - Pattern elements (prefix, suffix, separators, codes)
   - Examples of names that follow the pattern
   - Pattern adherence rate (what % of names follow the pattern?)

2. **Folder structure analysis**:
   - List all folder paths (groups) found in the scan data
   - What organizational scheme do they follow (by department, by integration, by function)?
   - Is the folder structure flat or hierarchical?
   - Are there orphaned recipes in root with no folder?
   - Do folder names use consistent formatting (Title Case, snake_case, etc.)?

3. **Connection naming analysis**:
   - Do connection names include the environment (prod, staging, dev)?
   - Do connection names include the purpose or system being connected to?
   - Are connection names consistent across recipes that use the same connection?
   - Are there connection names that could cause environment confusion (e.g., "salesforce" without environment qualifier)?

4. **Recipe naming analysis**:
   - Do recipe names describe the integration flow (source, target, action)?
   - Are there naming prefixes or codes (e.g., numbering, department codes)?
   - Are callable/worker recipes distinguishable from main/orchestrator recipes?
   - Are API recipes and webhook recipes clearly identified in names?

5. **Naming violations**: Identify names that deviate from the expected patterns:
   - Generic or uninformative names (e.g., "Recipe 1", "Test", "Copy of...")
   - Inconsistent separators (mix of underscores, hyphens, spaces, dots)
   - Missing elements (connection without environment, recipe without purpose)
   - Conflicting conventions (some snake_case, some camelCase, some Title Case)
   - Names with version indicators suggesting duplicates ("v2", "new", "old", "backup")

6. **Property scope analysis**:
   - Which properties are account-scoped (shared across all projects) vs project-scoped?
   - Do property names indicate their scope or environment?
   - Are there properties that should be environment-specific but are not?
   - Is the naming convention for properties consistent?

7. **Topic naming analysis**:
   - Do topic names clearly indicate the event type and domain?
   - Are topic names discoverable by potential subscribers?
   - Is there a consistent naming scheme across all topics?

8. **Consistency score and recommendations**: Measure overall naming consistency and provide actionable improvements.
