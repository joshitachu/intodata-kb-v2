You are analyzing a Workato integration project. Your task is to produce a **Data Quality & Validation Analysis** -- a comprehensive catalog of all validation rules, null handling patterns, data cleansing logic, and quality gates embedded in the recipes in this chunk.

## Workato Context
Data quality logic in Workato is implemented through several mechanisms:

- **Datapill formula validation**: Ruby-like methods on datapills serve as inline validation:
  - `.present?` -- checks if value is non-null and non-empty (returns true/false)
  - `.blank?` -- checks if value is null, empty string, or whitespace-only
  - `.presence || default` -- returns value if present, otherwise uses default
  - Ternary: `field.present? ? field : "UNKNOWN"` -- conditional default assignment
  - Type guards: `.to_i` (string to integer), `.to_f` (string to float), `.to_date` (string to date) -- these can fail silently on invalid input, returning 0 or nil instead of raising errors

- **Conditional branches as validation gates**: `if`/`elsif`/`else` blocks (WorkatoCondition_if, WorkatoCondition_elsif, WorkatoCondition_else) can serve as validation checkpoints before critical actions. Conditions compare datapills against expected values, patterns, or ranges. In the scan data, conditions appear in the block tree with operator/value pairs.

- **Lookup table cross-referencing**: `lookup_table_entry` actions validate referential integrity by checking that a value exists in a reference table. A failed lookup (no match) can indicate invalid data. The recipe's response to a failed lookup (skip, default, stop) determines the validation severity.

- **WorkatoStop as assertions**: `stop` actions (WorkatoStop component type) can halt recipe execution when validation fails. Stop with error message acts as an assertion -- "if this data is invalid, halt immediately." Stop actions in conditional branches act as quality gates.

- **Monitor/Catch as validation layers**: Wrapping actions in monitor/catch blocks provides a defense layer -- if a downstream system rejects data (e.g., 422 validation error from an API), the catch block can log the invalid data and continue processing valid records.

- **Type coercion risks**: Workato auto-converts between compatible types, but explicit conversions can fail:
  - `.to_i` on non-numeric string returns 0 (silent data corruption)
  - `.to_f` on non-numeric string returns 0.0 (silent data corruption)
  - `.to_date` on malformed date string returns nil (silent null injection)
  - These silent failures are dangerous because no error is raised -- bad data propagates downstream.

- **String cleansing methods**: `.strip` (trim whitespace), `.upcase`/`.downcase` (case normalization), `.gsub(pattern, replacement)` (regex substitution), `.split(delimiter)` (tokenization), `.truncate(length)` (length enforcement).

- **Database constraints**: When recipes write to databases, DB-level constraints (NOT NULL, UNIQUE, CHECK, FOREIGN KEY) provide a final validation layer. Constraint violations cause action failures that should be caught by monitor/catch blocks.

- **Layered defense best practice**: The recommended pattern is: conditional validation (check before action) -> monitor/catch with retry (handle transient failures) -> stop on unrecoverable conditions (halt if data is fundamentally invalid) -> targeted notification (alert on failures).

## What to Extract

1. **Validation rules**: For every validation check in the recipes:
   - Rule ID (unique identifier, e.g., DQ-001)
   - Recipe and step where the rule is implemented
   - Rule type (null_check, presence_check, range_check, format_validation, referential_integrity, type_validation, business_rule)
   - Rule description in plain English
   - Expression or condition that implements the rule
   - Severity (CRITICAL = recipe should stop, HIGH = record skipped, MEDIUM = default applied, LOW = warning logged)
   - Action on failure (stop recipe, skip record, apply default, log warning, send notification)

2. **Null/blank handling patterns**: For each field processed:
   - Is `.present?` or `.blank?` used to check the field?
   - What happens when the field is null/blank? (default value, skip, stop)
   - What default value is used? Is it business-meaningful or a technical placeholder?
   - Is `.presence || default` used for concise null-coalescing?

3. **Data cleansing transformations**: For every cleansing operation:
   - Field affected and recipe location
   - Cleansing method (`.strip`, `.upcase`, `.downcase`, `.gsub()`, `.truncate()`)
   - Purpose (standardization, normalization, sanitization)
   - Whether cleansing is applied consistently across recipes that handle the same field

4. **Type coercion risks**: Identify unsafe type conversions:
   - `.to_i` without prior `.present?` check (returns 0 on non-numeric input)
   - `.to_f` without prior `.present?` check (returns 0.0 on non-numeric input)
   - `.to_date` without format validation (returns nil on malformed dates)
   - Implicit Workato auto-conversions that may lose precision

5. **Referential integrity via lookup tables**: For each lookup_table_entry action:
   - What reference table is consulted?
   - What field is used as the lookup key?
   - What happens on lookup miss (no match)? Is the recipe resilient to missing references?
   - Could stale lookup table data cause silent data quality issues?

6. **Quality gates (stop actions as assertions)**: For each WorkatoStop in a validation context:
   - What condition triggers the stop?
   - Is it stop-with-error or stop-with-success?
   - What error message is provided?
   - What data condition does it guard against?

7. **Quality score per recipe**: Rate each recipe's data quality coverage:
   - **EXCELLENT**: Comprehensive validation (null checks, type validation, referential integrity, cleansing) with layered defense
   - **GOOD**: Most critical fields validated, some cleansing, error handling present
   - **FAIR**: Partial validation -- some null checks but gaps in coverage
   - **POOR**: Minimal or no validation -- data flows through unchecked
