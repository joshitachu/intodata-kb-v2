You are analyzing a Workato integration project. Your task is to produce a **Performance Profile** -- identify task consumption hotspots, optimization opportunities, polling inefficiencies, and resource-intensive patterns based on recipe structure, action types, loop analysis, and batch usage.

## Workato Context
Performance in Workato is governed by the task consumption model and recipe execution constraints:

- **Task consumption model**: Every action step that executes consumes 1 Workato task. This is the primary cost metric.
  - A recipe with 10 actions = 10 tasks per run.
  - **Batch actions** (bulk create, bulk update, bulk upsert) consume only 1 task regardless of record count (100x reduction vs per-record actions in a loop).
  - **Foreach loops multiply tasks**: A foreach loop over N items with M actions inside = N * M tasks per run. A loop over 1000 items with 3 actions = 3000 tasks per run.
  - **Conditional branches**: Only the executed branch consumes tasks -- skipped branches consume 0 tasks.
  - **Trigger step**: The trigger (step 0) does NOT consume a task.

- **Polling interval optimization**: Polling triggers (new_record, updated_record) run on configurable intervals:
  - Default: 5 minutes (smallest standard interval)
  - Configurable: 6 hours, 1 day, 30 days, or custom cron
  - Shorter intervals = more frequent runs = more task consumption (even if no new records)
  - Real-time alternatives: webhooks (0 polling cost), event topics (0 polling cost), API triggers (on-demand)

- **Batch vs single-record actions**: The biggest optimization lever:
  - **Single-record in foreach**: `foreach(records) -> create_record` = N tasks for N records
  - **Batch action**: `bulk_create(records)` = 1 task for N records
  - Batch triggers + batch actions = most efficient but failures affect entire batch (no per-record isolation)
  - Single-record triggers = least efficient but isolate failures per record

- **Lookup table vs search_records**: Performance trade-off for reference data:
  - `lookup_table_entry` = in-memory lookup, very fast, 1 task
  - `search_records` = API call to external system, slower, 1 task + network latency
  - Use lookup tables for frequently accessed, slowly changing reference data

- **Foreach loop optimization**:
  - Consolidate variable creation into a single "Create variables" step (1 task vs N tasks for N variables)
  - Use upsert instead of search + conditional update/insert (1 action vs 2-3 actions per record)
  - Use batch actions inside loops when the provider supports it

- **Memory and streaming**:
  - Recipe containers have finite memory -- avoid loading entire large files into memory
  - Use streaming actions for files >100MB (avoids memory limits)
  - Do NOT use `bytesize` formula on large files -- it forces full file download into memory
  - Collections should NOT be used for CSV parsing -- use dedicated CSV connector or database bulk load

- **Database optimization**:
  - Stored procedures for server-side data transformation (reduces task count -- 1 task for complex logic)
  - Trigger tables need a unique key + sorted column (e.g., `updated_at`) for reliable polling
  - Batch SQL operations (bulk INSERT, MERGE) instead of per-row operations in loops

## What to Extract

1. **Task consumption profile per recipe**: For each recipe:
   - Total action step count (steps that consume tasks)
   - Trigger type and polling interval (if polling)
   - Foreach loops: list size estimate, actions per iteration, total task multiplication
   - Estimated tasks per run (single execution)
   - Estimated tasks per day (based on trigger frequency)

2. **Foreach loop analysis**: For every foreach loop:
   - What list is being iterated (datapill source, estimated size)
   - How many actions are inside the loop body
   - Task multiplication factor (list_size * actions_per_iteration)
   - Whether batch actions could replace the loop
   - Whether the loop contains unnecessary steps (variable creation, redundant lookups)

3. **Batch action opportunities**: Identify recipes where single-record actions in loops could be replaced with batch actions:
   - Current: foreach -> create_record (N tasks)
   - Recommended: bulk_create (1 task)
   - Estimated task savings

4. **Polling interval assessment**: For each polling trigger:
   - Current polling interval
   - Whether the interval is appropriate for the data volume and latency requirements
   - Whether a webhook or event-driven trigger would be more efficient
   - Estimated task savings from interval optimization

5. **Lookup optimization**: Compare search_records vs lookup_table usage:
   - search_records actions that query slowly-changing reference data (should be lookup tables)
   - lookup_table_entry actions used appropriately
   - Database stored procedures that could replace multiple search + transform steps

6. **Memory-intensive patterns**: Identify recipes at risk of memory issues:
   - Large file processing without streaming
   - `bytesize` formula usage (forces full download)
   - Collections used for CSV parsing
   - Foreach loops over very large lists (>10K items)

7. **Slow recipe candidates**: Rank recipes by estimated task consumption and execution time:
   - Which recipes consume the most tasks per run?
   - Which recipes will scale poorly as data volume grows?
   - Which recipes should be optimized first (highest impact)?
