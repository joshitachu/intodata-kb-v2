You are analyzing a Workato integration project. Your task is to produce a **Reusability & Refactoring Analysis** -- identify duplicated logic, opportunities to extract shared recipe functions, code smells, unused assets, and create a refactoring roadmap to improve maintainability and reduce technical debt.

## Workato Context
Workato projects accumulate technical debt as they grow. Key reusability mechanisms and anti-patterns:

- **Recipe Functions** (post-Dec 2021): The modern reuse mechanism, replacing legacy callable recipes. Recipe functions are focused on reusability with simpler design. They do NOT create API endpoints (use API recipes for that). Existing legacy callable recipes still work but new ones cannot be created. RLCM packages export recipe functions alongside recipes, connections, and custom connectors.

- **Legacy Callable Recipes**: Pre-Dec 2021 mechanism for recipe-to-recipe invocation. Still functional but superseded by recipe functions. Projects using only callable recipes may benefit from migrating to recipe functions for simpler dependency management.

- **Custom Adapter reuse**: Custom adapters (Ruby SDK connectors) can define reusable methods via `call(method_name, args)` and shared `object_definitions`. Well-designed adapters follow DRY principles with reusable methods. Poorly designed adapters duplicate HTTP call patterns, inline credentials, and use static object definitions instead of dynamic ones.

- **Connection sharing**: Connections are workspace-level resources. Consistent naming (`{App} - {Environment}`) enables reuse across recipes and clean RLCM deployment. Duplicate connections for the same system waste connection slots and create configuration drift.

- **Properties for parameterization**: Account properties and project properties externalize configuration (URLs, thresholds, feature flags). Recipes that hardcode values instead of using properties are not portable across environments.

- **Common code smells in Workato**:
  - **God recipes** (>20 steps): Recipes that handle too many concerns -- should be decomposed into orchestrator + worker recipe functions.
  - **"Copy of..." clones**: Recipes duplicated via copy-paste, creating identical logic that drifts over time. Look for recipe names starting with "Copy of" or very similar step structures across recipes.
  - **Hardcoded values**: URLs, IDs, email addresses, thresholds embedded directly in recipe step inputs instead of using properties or lookup tables.
  - **Orphaned/inactive recipes**: Recipes with `active: false` or never called by any other recipe -- potential dead code.
  - **Unused custom adapters**: Adapters defined but not referenced by any recipe.
  - **`puts` statements in adapter code**: Debug logging left in production custom adapter Ruby code.
  - **Inconsistent naming**: Mix of naming conventions within the same project (some recipes follow `{Source} to {Target}`, others use ad-hoc names).
  - **Duplicated datapill formulas**: The same formula chain (e.g., `.strip.upcase`, `.present? ? field : 'default'`) repeated across many recipes instead of being encapsulated in a recipe function or custom adapter method.

- **Custom adapter best practices**:
  - `snake_case` for all naming (methods, fields, object definitions)
  - DRY with reusable methods and shared `object_definitions`
  - `control_type: password` for sensitive fields (never display in plain text)
  - Never hardcode Client IDs/Secrets in adapter code
  - Validate inputs in `execute` lambda (prevent injection/path traversal)
  - Do not suppress exceptions -- use `after_error_response` to surface HTTP errors
  - Dynamic object definitions preferred over static (reduces maintenance when API schemas change)

## What to Extract

1. **Duplicated datapill formulas**: For every formula expression that appears in multiple recipes:
   - Formula text
   - What it does (plain English)
   - Where it appears (recipe names, step references)
   - How many times it is duplicated
   - Recommended refactoring (extract to recipe function, encapsulate in adapter)

2. **Duplicated recipe structures**: Identify sets of recipes with similar step structures:
   - Pattern description (what the recipes do)
   - Recipes that follow this pattern
   - What varies between them (connection names, object types, field mappings)
   - Recommended refactoring (parameterized recipe function, shared callable)

3. **Recipe function / callable recipe usage assessment**:
   - Which recipe functions exist and how often are they called?
   - Which legacy callable recipes exist? Should they be migrated to recipe functions?
   - Are there recipe functions defined but never used (dead code)?
   - Are there reuse opportunities (similar logic in multiple recipes that could be a shared function)?
   - Underutilization assessment: are recipe functions being used to their potential?

4. **Custom adapter reuse analysis**: For each custom adapter:
   - Are shared methods (`call(method_name)`) used for DRY code?
   - Are `object_definitions` shared across actions/triggers?
   - Is the adapter used by multiple recipes or just one?
   - Code quality: `snake_case` naming, `control_type: password`, no hardcoded secrets, dynamic vs static object definitions
   - Are there `puts` statements (debug logging) left in production code?

5. **Connection analysis**: For workspace connections:
   - Duplicate connections (same provider/system, different names)
   - Connection naming consistency (`{App} - {Environment}` pattern)
   - Connections used by only one recipe (over-provisioned)
   - Connections used by many recipes (shared infrastructure)

6. **Code smells**: Identify anti-patterns:
   - God recipes (>20 action steps)
   - "Copy of..." clones (duplicated recipes)
   - Hardcoded values that should use properties or lookup tables
   - Orphaned/inactive recipes (never called, `active: false`)
   - Unused custom adapters
   - `puts` statements in adapter code
   - Inconsistent naming conventions
   - Deeply nested block trees (>5 levels)

7. **Reusability score**: Rate the project (1-10) based on:
   - Recipe function / callable recipe usage
   - Custom adapter code quality and reuse
   - Connection management
   - Property usage (parameterization level)
   - Code duplication level

8. **Refactoring roadmap**: Prioritized list of improvements:
   - What to refactor
   - Why (benefit)
   - Effort (low, medium, high)
   - Impact (task savings, maintainability improvement, consistency gain)
   - Risk (could refactoring break something?)
