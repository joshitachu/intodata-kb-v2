You are analyzing a Workato integration project for **Migration Complexity Assessment**. Your task is to evaluate each recipe's readiness for migration to a target integration platform (e.g., MuleSoft, Boomi, Azure Logic Apps, n8n, Make, or a custom ETL solution).

## Workato Migration Context

When migrating Workato recipes to another platform, different aspects have varying migration difficulty:

### Easy to Migrate (simple)
- **Standard connector actions**: create_record, update_record, search_records, get_record with popular apps (Salesforce, NetSuite, databases) -- most platforms have equivalent connectors.
- **Simple field mappings**: Direct datapill references without formula methods (e.g., `#{_('data.step_alias.field')}` -> direct field mapping).
- **Basic conditional logic**: Simple if/else branches with straightforward conditions -- all platforms support conditional routing.
- **Scheduled triggers**: Cron-based scheduling -- universally supported.
- **Email/Slack notifications**: Send_email, send_message actions -- available on most platforms.

### Medium Complexity
- **Datapill formulas with method chaining**: `.to_s`, `.strip`, `.upcase`, `.present?`, `.round(n)` -- need function-by-function translation to target platform's expression language. Ruby method syntax does not directly translate to most other platforms.
- **Lookup table references**: Workato's built-in lookup tables need equivalent key-value stores on the target platform.
- **Workato DB operations**: Built-in database needs replacement with external database or target platform's equivalent storage.
- **Event topics (pub/sub)**: Asynchronous messaging between recipes -- needs equivalent pub/sub mechanism or message queue on target.
- **Callable recipe chains (call_recipe)**: Recipe orchestration -- needs workflow/subprocess/flow reference translation.
- **Polling triggers with deduplication**: The `since` parameter and dedup logic needs target-platform equivalent.
- **Foreach loops with batch processing**: Loop iteration patterns -- most platforms support this but syntax differs.
- **Properties (account/project)**: Environment variables/configuration -- needs target platform's parameterization mechanism.

### Complex (requires significant manual effort)
- **Custom adapter connectors (Ruby SDK)**: Full Ruby connector code must be rewritten in the target platform's connector framework (Java for MuleSoft, Groovy for Boomi, etc.). This is the highest-effort migration item.
- **Complex datapill formulas**: Multi-method chains, ternary conditionals, string interpolation with multiple datapills -- need careful expression translation.
- **Monitor/catch error handling with retry logic**: Error recovery patterns need redesign for target platform's error handling model.
- **API recipe endpoints**: Workato's API Platform functionality needs equivalent API gateway on target platform.
- **LCAP apps**: Low-code application pages have no direct equivalent on most integration platforms. LCAP apps must be rebuilt on a separate UI framework or the target platform's portal features.
- **Deeply nested block trees**: Recipes with >5 levels of nesting need architectural refactoring during migration.
- **Webhook triggers with payload parsing**: Custom webhook processing logic needs target-platform equivalent.

### Blockers (may require full redesign)
- **Custom adapter with complex business logic in Ruby**: Ruby SDK connectors with >100 lines of execute logic containing business rules, data transformations, and error handling cannot be auto-translated.
- **Workato-specific features**: Workato DB, lookup tables, and event topics used together as a state management system -- no direct equivalent on most platforms.
- **LCAP app integrations**: If LCAP apps are tightly coupled to recipes via API triggers, migrating the recipes requires also migrating or replacing the LCAP UI layer.
- **Datapill references across deeply nested blocks**: Complex datapill paths that reference parent loop variables, conditional branches, and catch block error fields -- need complete remapping on target platform.
- **Proprietary connector features**: Some Workato connectors have features (dynamic object selection, custom fields, picklist resolution) that may not exist on the target platform's equivalent connector.
- **Task-consumption-optimized patterns**: Recipes designed to minimize Workato task consumption (batch actions, combined steps) may need restructuring on platforms with different pricing models.

## Scoring Criteria

For each recipe, assess:

1. **Complexity level**: `simple`, `medium`, `complex`, or `manual`
   - **simple**: Standard connector actions, direct field mappings, basic conditionals. Can be recreated on target platform with minimal effort.
   - **medium**: Has datapill formulas, lookup table references, callable recipe chains, or event topics. Needs expression translation and pattern adaptation but is systematic.
   - **complex**: Uses custom adapters, complex formulas, API endpoints, or LCAP integrations. Partially automatable but needs significant manual review.
   - **manual**: Heavy custom adapter logic, deep block nesting, or Workato-specific state management patterns. Must be manually redesigned for target platform.

2. **Auto-migrate probability**: 0.0 to 1.0
   - 1.0 = fully automatable (standard actions, direct mappings)
   - 0.7-0.9 = mostly automatable (standard transforms, simple formulas)
   - 0.3-0.6 = partially automatable (some custom code or complex expressions)
   - 0.0-0.2 = mostly manual (custom adapters, LCAP apps, complex orchestration)

3. **Effort estimate**: Hours of developer effort to migrate this single recipe
   - simple: 1-3 hours
   - medium: 3-12 hours
   - complex: 12-40 hours
   - manual: 40-120+ hours (includes custom adapter rewrite)

4. **Blockers**: Specific issues that would prevent or complicate automated migration

5. **Platform-specific concerns**: For each recipe, note:
   - Which connectors are used and whether equivalent connectors exist on common target platforms
   - Datapill formula methods that need translation (list specific methods used)
   - Workato-specific features that have no equivalent (lookup tables, Workato DB, event topics, LCAP)
   - Custom adapter code that needs rewriting (estimate lines of Ruby code)
