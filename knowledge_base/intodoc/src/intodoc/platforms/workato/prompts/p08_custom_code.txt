You are analyzing a Workato integration project. Your task is to produce a **Custom Code Analysis** -- a detailed examination of all Ruby code in custom adapter files, SDK connector definitions, and any embedded code blocks, identifying hidden business rules, security implications, and maintainability risks.

## Workato Context
Workato allows custom code through custom adapters (connectors) built with the Workato Connector SDK, which uses Ruby:

- **Custom Adapters (Routine objects with source_code)**: These are the primary vehicle for custom code in Workato. Each custom adapter is a Ruby file that defines a connector using Workato's SDK DSL. The adapter's source code is stored in `*.custom_adapter.json` files and parsed into `Routine` objects with `source_code` containing the full Ruby code. In the scan data, these appear as routines with names prefixed `adapter_`.

- **Connector SDK structure**: A custom adapter defines several key sections:
  - **connection**: Authentication configuration -- how to connect to the target system
    - `fields`: Input fields for connection credentials (API key, username, password, base URL)
    - `authorization`: Auth strategy (basic, api_key, oauth2, custom)
    - `base_uri`: Dynamic base URL construction
    - `apply`: How credentials are applied to each request (headers, query params, body)
  - **test**: A lambda that verifies the connection works (e.g., GET /api/me)
  - **actions**: Hash of action definitions, each with:
    - `title` and `description`: User-facing metadata
    - `input_fields`: Dynamic input field definitions (can depend on other field values)
    - `execute`: The core logic -- makes HTTP requests, transforms data, handles errors
    - `output_fields`: Defines the schema of the action's output
    - `sample_output`: Example output for the recipe editor
  - **triggers**: Hash of trigger definitions with poll/webhook logic:
    - `poll`: Polling logic with `since` parameter for incremental polling
    - `webhook_notification`: Processing of incoming webhook payloads
    - `dedup`: Deduplication logic to prevent processing the same event twice
  - **object_definitions**: Reusable schema definitions referenced by actions and triggers
  - **pick_lists**: Dynamic dropdown lists for the recipe editor

- **Ruby SDK methods**: Custom adapters use Workato-specific Ruby methods:
  - `get(url)`, `post(url, payload)`, `put(url, payload)`, `delete(url)` -- HTTP methods
  - `.headers(hash)`, `.params(hash)` -- Request configuration
  - `.response_format_json`, `.response_format_xml` -- Response parsing
  - `.after_error_response(code) { |_, body, _, message| ... }` -- Error handling
  - `workato.parse_json(string)`, `workato.encode_json(hash)` -- JSON utilities
  - `call(method_name, args)` -- Invoke shared methods within the adapter

- **Differences from Talend custom code**: Unlike Talend's tJava/tJavaRow/tJavaFlex (which are inline Java snippets within jobs), Workato's custom code is concentrated in adapter files that act as self-contained connectors. There are no inline code blocks in recipes -- all custom logic lives in adapters. Recipe steps use these adapters as if they were built-in connectors.

## What to Extract

1. **Custom adapter overview**: For each custom adapter (Routine), provide:
   - Adapter name and file location
   - Target system/API it connects to
   - Authentication method (basic, oauth2, api_key, custom)
   - Summary of what the adapter does (1-2 sentences)

2. **Connection configuration analysis**: For each adapter's `connection` block:
   - What credential fields are defined (API key, username, password, token, base URL)
   - How credentials are applied to requests (headers, query params, body)
   - Whether the base URL is configurable (parameterized) or hardcoded
   - Whether the test method validates the connection properly

3. **Action definitions analysis**: For each action in each adapter:
   - Action name and description
   - Input fields and their types
   - Full `execute` code (include verbatim)
   - Plain-English explanation of what the execute block does
   - HTTP endpoints called (method, URL pattern)
   - Data transformation logic applied to request or response
   - Error handling within the execute block (after_error_response, rescue blocks)
   - Business rules embedded in the logic (conditional processing, data validation, special-case handling)

4. **Trigger definitions analysis**: For each trigger in each adapter:
   - Trigger name and type (polling or webhook)
   - Polling logic: what is the `since` parameter? How is incremental polling implemented?
   - Webhook processing: how is the payload parsed and validated?
   - Deduplication logic: what field is used for dedup? Is it reliable?

5. **Schema/object definitions**: For each object_definition:
   - What data structure does it represent?
   - What fields are defined with what types?
   - Are there dynamic field definitions (fields that depend on runtime values)?

6. **Security analysis of custom code**:
   - Does any code handle credentials, passwords, or API keys directly?
   - Are credentials stored in variables or logged?
   - Does any code disable SSL verification or bypass security checks?
   - Are API URLs hardcoded (breaking environment portability)?
   - Does the code build SQL queries or API paths via string interpolation (injection risk)?
   - Are there hardcoded secrets, tokens, or keys in the Ruby source?
   - Does the error handling expose sensitive information in error messages?

7. **Maintainability assessment**: For each adapter:
   - Code complexity: Is the code readable by a new developer?
   - Documentation: Are there comments explaining the business logic?
   - Code organization: Are shared methods extracted and reused?
   - Ruby idiom usage: Is the code using Ruby best practices or anti-patterns?
   - Testing: Is there a comprehensive test method, or just a minimal ping?
   - API version pinning: Are API endpoints versioned? What happens when the API changes?

8. **Hidden business rules catalog**: Extract every business rule found in custom code:
   - The rule in plain English
   - Where it is defined (adapter name, section, approximate location in code)
   - What data it affects
   - What would break if the rule changed
