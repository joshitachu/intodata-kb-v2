You are analyzing a Workato integration project. Your task is to produce an **Error Handling & Resilience Analysis** -- a thorough assessment of how each recipe handles failures, what happens when things go wrong, and where silent failures can occur.

## Workato Context
Workato provides several mechanisms for error handling, but unlike Talend's SUBJOB_ERROR triggers, Workato has NO automatic error propagation by default. Unhandled errors simply terminate the recipe run with a failed status in the job history. Without explicit error handling, there is no notification, no retry, and no recovery logic.

- **Monitor/Catch blocks**: The primary error handling mechanism. A `monitor` block (keyword "monitor") wraps steps that might fail. A paired `catch` block (keyword "catch") handles errors when any step inside the monitor throws an error. The catch block receives error datapills: error_message, error_type, error_step, error_input. Components in the scan data appear as `WorkatoMonitor` and `WorkatoCatch` component types.

- **WorkatoStop actions**: The `stop` keyword halts recipe execution immediately. It can be configured to mark the run as successful (stop with success) or failed (stop with error message). Stop actions in catch blocks provide controlled failure with a meaningful error message. Stop actions appear as `WorkatoStop` component type.

- **Action-level retry**: Individual actions can have retry configuration (automatic retry on transient errors with exponential backoff). This is configured per-step and not always visible in the export JSON.

- **Manual retry in catch blocks**: A `repeat` loop inside a catch block implements custom retry logic with control over retry count, delay, and fallback behavior.

- **Error notification patterns**: Common patterns in catch blocks include:
  - Sending an email (send_email action) with error details
  - Posting to Slack/Teams (send_message action) with error context
  - Writing to Workato DB or an error log table for audit trail
  - Publishing to an error event topic for centralized error handling

- **Callable recipe error propagation**: When recipe A calls recipe B via call_recipe, if recipe B fails and is not wrapped in a monitor/catch in recipe A, the error propagates up and terminates recipe A. This is similar to Talend's DIE_ON_CHILD_ERROR=true behavior. To handle callee failures gracefully, the call_recipe action must be inside a monitor/catch block.

- **Event topic subscriber failures**: If a subscriber recipe fails after receiving an event from a topic, the publisher is NOT notified. The failed event is NOT automatically retried. Failed subscriber runs appear only in job history and may go unnoticed without monitoring.

- **Foreach loop failures**: If an action inside a foreach loop fails on one item, the default behavior is to stop the loop and fail the recipe. There is no automatic "skip and continue" behavior unless the action is wrapped in monitor/catch within the loop body.

## What to Extract

1. **Recipe-level error handling rating**: For each recipe, assign a rating:
   - **GOOD**: Has monitor/catch blocks around critical actions, catch blocks include notification (email/Slack), error details are logged, stop-on-error provides clear messages, callable recipes are protected
   - **ADEQUATE**: Has some monitor/catch coverage but gaps exist (e.g., some critical actions unprotected, catch block only stops without notification)
   - **POOR**: Minimal error handling -- only one monitor/catch for the entire recipe or catch blocks that just stop without logging
   - **NONE**: No monitor/catch blocks detected -- all failures will terminate the recipe silently with only job history as evidence

2. **Monitor/Catch coverage analysis**: Map every monitor/catch pair:
   - Which steps are inside each monitor block (protected steps)
   - What the catch block does: notification? logging? retry? stop? continue?
   - Whether error datapills (error_message, error_step) are used in the catch block
   - Whether the catch block includes a stop action (controlled failure) or silently continues

3. **Unprotected critical actions**: Identify actions NOT inside any monitor/catch that should be protected:
   - Database write operations (create_record, update_record, run_sql)
   - External API calls (send_request)
   - File operations (upload_file, download_file)
   - Actions that modify data in target systems
   - call_recipe actions (callee failure will propagate up)

4. **Stop action analysis**: For each WorkatoStop component:
   - Where it is in the recipe (catch block, conditional branch, validation check)
   - Whether it stops with success or error
   - What error message is provided
   - Whether stopping at this point could leave data in an inconsistent state (e.g., partial writes)

5. **Error notification coverage**:
   - Which catch blocks send notifications (email, Slack, Teams)?
   - Which catch blocks log errors to persistent storage (Workato DB, external database)?
   - Which catch blocks have NO notification -- errors will only appear in job history
   - Is there a centralized error handling recipe or topic?

6. **Callable recipe error propagation**:
   - For each call_recipe action: is it inside a monitor/catch block?
   - If not, a callee failure will terminate the caller recipe
   - If yes, how does the catch block handle the callee failure?

7. **Loop error resilience**:
   - For foreach loops: are actions inside the loop wrapped in monitor/catch?
   - If not, one failed item will stop the entire loop and fail the recipe
   - If yes, what happens to failed items? Are they logged? Skipped? Retried?

8. **Event topic subscriber resilience**:
   - Do subscriber recipes have monitor/catch blocks?
   - If a subscriber fails, is there any dead-letter mechanism (error topic, Workato DB log)?
   - Could failed events be silently lost?

9. **Silent failure scenarios**: Identify specific scenarios where a failure would go completely unnoticed:
   - Recipe fails with no monitor/catch and no notification configured
   - Catch block swallows error (no notification, no logging, no stop)
   - Event topic subscriber fails without dead-letter handling
   - Foreach loop skips items without logging
   - Polling trigger misses records during downtime with no gap-detection
