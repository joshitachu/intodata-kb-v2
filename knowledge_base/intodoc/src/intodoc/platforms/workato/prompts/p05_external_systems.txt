You are analyzing a Workato integration project. Your task is to produce an **External Systems Catalog** -- a comprehensive inventory of every external system, service, database, API, and messaging channel that the recipes in this chunk connect to, along with connection details, usage patterns, and a topology diagram.

## Workato Context
Workato recipes interact with external systems through provider-based connections and HTTP actions:

- **Provider-based connections**: Each connection has a `provider` field identifying the app (e.g., "salesforce", "netsuite", "postgresql", "snowflake", "s3"). The provider maps to a standardized connection type. Connection metadata includes:
  - `provider`: The app identifier (e.g., "salesforce", "netsuite", "http")
  - `application`: The display name of the app
  - `authorization_type`: Auth method (e.g., "oauth2", "api_key", "basic", "custom")
  - `base_url`: For HTTP/REST connections, the base URL of the target API
  - `host`, `port`, `database`, `schema`: For database connections

- **Provider-to-type mapping**: Common provider mappings include:
  - salesforce -> Salesforce, netsuite -> NetSuite, postgresql -> PostgreSQL, mysql -> MySQL
  - snowflake -> Snowflake, bigquery -> BigQuery, redshift -> Redshift
  - s3 -> S3, gcs -> GCS, http -> HTTP/REST, workato_webhooks -> Webhook
  - sftp -> SFTP, smtp -> SMTP, jira -> Jira, slack -> Slack, teams -> MSTeams
  - sap -> SAP, oracle -> Oracle, mssql -> MSSQL, servicenow -> ServiceNow
  - hubspot -> HubSpot, marketo -> Marketo, stripe -> Stripe, quickbooks -> QuickBooks

- **HTTP custom requests**: `send_request` actions (HTTP calls) define custom API interactions with explicit URL, method, headers, and body. These may connect to systems not represented by dedicated connectors.

- **Webhook triggers**: `webhook` triggers expose a Workato URL that external systems call to push data into recipes. The external system is the caller.

- **API recipe endpoints**: Recipes with `api_trigger` expose REST endpoints that external systems can invoke. The recipe acts as a server.

- **Event topics**: Internal pub/sub channels. While not external systems, they represent messaging infrastructure that connects recipes asynchronously.

- **Lookup tables and Workato DB**: Internal Workato storage. Not external systems, but they serve as data persistence layers referenced by recipes.

- **Connection sharing**: Multiple recipes can share the same connection. A connection name like "salesforce_prod" may be used by 10+ recipes. Conversely, a recipe may use multiple connections (e.g., read from Salesforce, write to NetSuite).

## What to Extract

1. **External system inventory**: For every external system detected across all recipes in this chunk, provide:
   - System name (derived from connection name or HTTP URL)
   - System type (Salesforce, NetSuite, PostgreSQL, REST API, SFTP, etc.)
   - Provider identifier from the connection
   - Connection details: base_url, host, port, database, schema (as available)
   - Authentication method: oauth2, api_key, basic, custom, JWT, certificate
   - Whether the connection is a named reusable connection or an inline HTTP request

2. **Usage mapping**: For each external system:
   - Which recipes connect to it
   - What operations are performed (READ via triggers/search, WRITE via create/update, READ_WRITE, DELETE)
   - Which specific objects, tables, or endpoints are accessed
   - Whether the system is accessed via polling trigger, event-driven trigger, action, or HTTP request
   - Estimated request volume indicators (polling interval, foreach loop size, batch vs single-record)

3. **Criticality rating**: Rate each external system:
   - **CRITICAL**: Production systems written to where data loss or corruption would be severe; API endpoints exposed publicly
   - **HIGH**: Production systems read from as primary data sources; systems feeding downstream automations
   - **MEDIUM**: Staging/temporary storage, lookup/reference data, notification channels (Slack, email)
   - **LOW**: Development/test systems, optional integrations, logging-only connections
   - Explain the rationale for each rating

4. **Webhook and API exposure**: Catalog all inbound integration points:
   - Webhook triggers: What external systems push data into Workato? What payload schemas are expected?
   - API recipe endpoints: What endpoints are exposed? What methods? What authentication is configured?
   - Security: Are API endpoints protected by authentication? Are webhook URLs validated?

5. **Network topology**: Map the data flow between external systems through Workato:
   - Source systems (data originates here -- triggers and search actions)
   - Intermediate systems (staging, lookup, enrichment)
   - Target systems (final destination -- create/update/upsert actions)
   - Direction of data flow between systems

6. **Connection patterns**:
   - Which connections are shared across many recipes (high fan-out)?
   - Which recipes use many connections (high fan-in)?
   - Are there environment-specific connection naming patterns (prod vs staging vs dev)?
   - Are there connection names that suggest environment mismatch risks?

7. **Security observations**:
   - Connections using oauth2 vs basic auth vs api_key
   - HTTP connections without TLS (http:// instead of https://)
   - API recipes without authentication configured
   - Hardcoded URLs or credentials in recipe inputs (not in connections)
   - Connections with overly broad permissions
