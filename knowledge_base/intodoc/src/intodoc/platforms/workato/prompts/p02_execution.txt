You are analyzing a Workato integration project. Your task is to produce an **Execution Logic Analysis** -- a complete mapping of control flow, execution order, trigger conditions, and orchestration chains for every recipe in this chunk.

## Workato Context
In Workato, execution flow is governed by a recursive block tree structure within each recipe:

- **Trigger (step 0)**: The first block in every recipe. Defines what event starts the recipe. Types include: `new_record` (poll for new rows), `updated_record` (poll for changes), `scheduled_event` (cron-like timer), `webhook` (push-based HTTP callback), `api_trigger` (recipe exposed as REST endpoint), `new_event` (event topic subscriber), `new_file` (file/storage watcher). The trigger determines whether the recipe is polling-based (runs on intervals) or event-driven (runs on-demand).

- **Actions**: Processing steps that follow the trigger. Each action has a `keyword: "action"`, a `provider` (the app connector, e.g., salesforce, netsuite), and a `name` (the operation, e.g., create_record, search_records, run_sql). Actions execute sequentially within their block scope.

- **The `number` field**: Every block node has a `number` field that defines the step's position in the recipe. Step 0 is always the trigger. Steps are numbered sequentially as the block tree is flattened in depth-first order. The number field determines the execution order within a given block scope.

- **The `keyword` field**: Controls execution behavior:
  - `trigger` -- recipe entry point (step 0)
  - `action` -- perform an operation
  - `if` / `elsif` / `else` -- conditional branching (evaluate a boolean expression)
  - `foreach` -- iterate over a list of items (child steps execute once per item)
  - `repeat` -- repeat child steps N times or until a condition is met
  - `monitor` -- try block (wrap steps for error handling)
  - `catch` -- catch block (handle errors from paired monitor block)
  - `stop` -- halt recipe execution (with success or error status)

- **Block tree structure**: Each node can contain a `block` array of child nodes, creating a recursive tree. Control flow keywords (if, foreach, monitor) create nested scopes. Child steps execute within the scope of their parent keyword. For example, steps inside a `foreach` block execute once per list item; steps inside an `if` block execute only when the condition is true.

- **The `as` field**: Defines the step alias used in datapill references. This is the unique identifier for accessing a step's output downstream (e.g., `data.salesforce_1.account_name`).

- **Callable recipe chains (call_recipe)**: A recipe can invoke another recipe synchronously via `call_recipe` action (analogous to Talend's tRunJob). The caller pauses until the callee completes. Input parameters are passed and return values are received. This creates orchestration chains: an orchestrator recipe calling multiple worker sub-recipes in sequence.

- **Event-driven chains**: Recipes connected via event topics create asynchronous execution chains. A publisher recipe's `publish_event` action triggers subscriber recipes that have `new_event` triggers on the same topic. Subscribers execute independently and asynchronously.

## What to Extract
For each recipe in this chunk:

1. **Trigger analysis**: What triggers this recipe? Trigger type, provider, polling interval (if applicable), event topic (if subscriber), API method/URL (if API trigger). Is this polling-based or event-driven?

2. **Block tree structure**: Map the complete block tree showing all nesting levels. For each node, document: keyword, provider, action name, step number, nesting depth, and the `as` alias.

3. **Conditional branches**: For every `if/elsif/else` block, document:
   - The condition expression (from the `input.conditions` array)
   - The operand type (AND/OR)
   - What steps execute in each branch
   - Whether all branches are covered (is there an else?)

4. **Loop structures**: For every `foreach` and `repeat` block:
   - What list/collection is being iterated (source datapill)
   - What steps execute per iteration
   - Whether there are batch controls or pagination
   - Risk of unbounded iteration (large lists without limits)

5. **Monitor/Catch blocks**: For every `monitor` (try) and `catch` pair:
   - Which steps are protected by the monitor
   - What recovery logic is in the catch block
   - Whether the catch block includes notification, logging, retry, or stop

6. **call_recipe orchestration**: For each `call_recipe` action:
   - Which callable recipe is being invoked (recipe_id resolution)
   - What input parameters are passed
   - Whether return values are used downstream
   - Position in the execution sequence

7. **Execution order**: Produce a numbered, sequential execution order for the recipe, accounting for:
   - Trigger (always first)
   - Sequential actions in order of step number
   - Nested blocks (indent to show scope)
   - Conditional branches (show which path)
   - Loop iterations (mark as repeated)

8. **Stop points**: Identify all `stop` actions:
   - What triggers them (condition, catch block, validation failure)
   - Whether they stop with success or error
   - What error message is provided

9. **Dead paths**: Steps or blocks that are present but unreachable (e.g., steps after an unconditional stop, empty else branches, branches with impossible conditions).
