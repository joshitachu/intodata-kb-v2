You are analyzing a Workato integration project. Your task is to produce a **Component Inventory** -- a comprehensive catalog of every recipe, connection, topic, API endpoint, LCAP app, lookup table, custom adapter, and dependency in this chunk.

## Workato Context
In Workato, automation is built from several asset types:
- **Recipes**: The primary automation unit. Each recipe has a trigger (step 0) and a tree of action steps. Recipes are organized in folders and can call each other via callable recipes (call_recipe).
- **Connections**: App connections that encapsulate authentication credentials for external systems (Salesforce, NetSuite, PostgreSQL, REST APIs, etc.). Connections are identified by a `provider` field (e.g., "salesforce", "netsuite", "postgresql") and mapped to a standardized connection type. Multiple recipes can share the same connection.
- **Event Topics**: Pub/sub messaging channels for asynchronous communication between recipes. A publisher recipe sends events to a named topic; subscriber recipes trigger on new events from that topic.
- **API Endpoints**: Recipes exposed as REST API endpoints via Workato's API Platform. They use the `api_trigger` keyword and define request/response schemas.
- **LCAP Apps**: Low-code application pages that provide web-based UIs interacting with recipes via API triggers or direct recipe calls.
- **Lookup Tables**: Static reference data tables for mapping codes, storing configuration values, or maintaining small reference datasets.
- **Workato DB Tables**: Built-in database tables for persistent state storage, tracking recipe state, intermediate results, or audit logs.
- **Custom Adapters**: Custom connector SDK code written in Ruby that extends Workato's built-in connector library. These define connection settings, actions, triggers, and object definitions.
- **Properties**: Account-level or project-level configuration variables (account_property, project_property) that parameterize recipes across environments.
- **Common Schemas**: Shared data models (workato_schema) reused across recipes and adapters.

Component types follow the pattern `WorkatoTrigger_{provider}_{action}` for triggers and `WorkatoAction_{provider}_{action}` for actions. Control flow uses `WorkatoCondition_if/elsif/else`, `WorkatoLoop_foreach/repeat`, `WorkatoMonitor` (try), `WorkatoCatch` (catch), and `WorkatoStop`.

Recipe call chains use `call_recipe` actions (analogous to Talend's tRunJob) where one recipe invokes a callable sub-recipe and optionally receives return data.

## What to Extract
For each recipe (job) in the chunk, identify:

1. **All components** with their type, unique name (the `as` field / step alias), provider, action name, and purpose
2. **Dependencies**: which recipes call which (call_recipe refs), which connections are used (provider references), which event topics are published to or subscribed from
3. **Referenced by**: which parent recipes call this recipe via call_recipe
4. **Connection usage**: which connections each recipe uses, identified by provider name
5. **Orphaned components**: components with no incoming or outgoing connections in the block tree
6. **Missing references**: call_recipe refs pointing to non-existent recipes, provider refs to missing connections, topic refs to undefined topics

Also catalog all non-recipe assets in the chunk:
7. **Connections**: name, provider, connection type, authorization type, base URL
8. **Event Topics**: name, schema, publishers, subscribers
9. **API Endpoints**: name, method, URL pattern, request/response schemas
10. **LCAP Apps**: name, page count, recipe bindings
11. **Lookup Tables**: name, columns, estimated row count
12. **Custom Adapters**: name, actions defined, triggers defined
13. **Properties**: account vs project scope, name, value pattern
