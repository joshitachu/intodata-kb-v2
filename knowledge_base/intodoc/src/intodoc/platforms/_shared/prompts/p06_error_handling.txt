You are analyzing an integration project built on a data integration platform. Your task is to produce an **Error Handling & Resilience Analysis** -- a thorough assessment of how each job handles failures, what happens when things go wrong, and where silent failures can occur.

## Integration Platform Context
Integration platforms provide several mechanisms for error handling, but many are optional and frequently misconfigured:
- **Step group failure triggers**: Fire when a step group fails. If a step group has no failure trigger connection, the error may be silently swallowed (the job continues) or cause an unhandled crash depending on the component and die-on-error settings.
- **Component-level failure triggers**: Fire when a single component within a step group fails. More granular than step-group-level triggers.
- **Abort/die components**: Explicitly terminate the job with an error code and message. Connected via failure triggers. Used for controlled failure with a meaningful error message.
- **Warning components**: Log a warning message but do NOT stop the job. Used for non-fatal issues that should be recorded.
- **Logging components**: Print data to the console/log. Often connected to error/reject flows to log problematic rows.
- **Error capture components**: Catch all log events (warnings, fatal errors, exceptions) and route them to a flow for processing (e.g., writing to an error log table).
- **Statistics capture components**: Capture job execution statistics (start time, end time, row counts) for monitoring.
- **Die on error (component setting)**: Each component typically has a "die on error" option. When enabled, any error in that component kills the entire job. When disabled, the error is caught and can be handled by a failure trigger or silently ignored.
- **Child error propagation (orchestration setting)**: When a parent job calls a child job via orchestration, this setting determines whether the parent dies if the child fails. If disabled, a child failure is silently ignored.
- **Try-catch-finally blocks**: Some platforms provide explicit exception handling components that wrap a block of steps in try-catch-finally semantics.
- **Reject flows**: Transformation and join components may have "reject" output links that capture rows that failed processing (e.g., lookup misses, type conversion errors). If reject flows are not connected, failed rows are silently dropped.
- **Commit/rollback**: Database components can be configured with commit intervals and rollback-on-error behavior. Missing rollback configuration can lead to partial writes on failure.

## What to Extract

1. **Job-level error handling rating**: For each job, assign a rating:
   - **GOOD**: Has failure handlers on critical step groups, uses abort/die for fatal errors, has centralized error logging, reject flows are connected, database operations have rollback configured
   - **ADEQUATE**: Has some error handling but gaps exist (e.g., some step groups lack error handlers, not all reject flows connected)
   - **POOR**: Minimal error handling -- only die-on-error settings, no explicit failure handlers
   - **NONE**: No error handling mechanisms detected -- all failures will either crash ungracefully or be silently ignored

2. **Error handling components**: For each job, list every error-related component:
   - Abort/die components: where they are, what triggers them, what message/error code they produce
   - Warning components: what conditions trigger warnings
   - Logging components: what data is being logged and why
   - Error capture components: whether present, what they capture, where they send captured logs
   - Statistics capture components: whether present, where statistics are sent

3. **Failure trigger coverage**: Map every failure trigger:
   - Which step groups HAVE error handlers and what they do
   - Which step groups are MISSING error handlers (these are silent failure risks)

4. **Die-on-error settings**: For each component:
   - Is "die on error" enabled or disabled?
   - If disabled, is there a component-level failure handler? If not, errors will be silently swallowed.

5. **Child error propagation in orchestration**: For each orchestration call:
   - Is child error propagation enabled?
   - If disabled, the parent job will continue even if the child fails -- flag this as a risk.

6. **Reject flow analysis**: For each transformation and join component:
   - Are reject outputs connected to anything?
   - If not, how many rows could be silently dropped?
   - What kinds of failures produce rejects (lookup misses, type errors, null values)?

7. **Database transaction safety**:
   - Are database outputs configured with commit intervals?
   - Is rollback-on-error configured?
   - Could a failure result in partial data writes (some rows committed, others not)?

8. **Silent failure scenarios**: Identify specific scenarios where a failure would go completely unnoticed:
   - Step group fails but no failure handler and next step group runs via separate trigger chain
   - Orchestration child fails but child error propagation is disabled
   - Transformation reject rows dropped silently
   - Die-on-error disabled with no component-level failure handler

## Instructions

- **Be thorough and pessimistic.** Assume any unhandled error path WILL eventually fail silently.
- Flag every missing error handler, every unconnected reject flow, every disabled die-on-error setting.
- Silent failures are the most dangerous -- a job that crashes loudly is better than one that silently produces incomplete data.
- For each silent failure scenario, assess how difficult it would be to detect the problem (detection difficulty).
- Consider the cascading effects of failures -- a silent failure in a parent job affects all downstream child jobs and consumers.
