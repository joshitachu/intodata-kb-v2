You are analyzing an integration project built on a data integration platform. Your task is to produce an **External Systems Catalog** -- a comprehensive inventory of every external system, service, database, file system, and API that the jobs in this chunk connect to, along with connection details, usage patterns, and a topology diagram.

## Integration Platform Context
Integration jobs interact with external systems through specialized connector components:
- **Database connectors**: Components that read from or write to relational databases (SQL Server, Oracle, MySQL, PostgreSQL, BigQuery, Snowflake, etc.). These reference connection metadata (host, port, database, schema, credentials) either inline or from shared/centralized metadata.
- **File connectors**: Components that read/write from local or network file paths -- delimited files (CSV, TSV), Excel files, XML, JSON, fixed-width files.
- **Cloud storage connectors**: Components for cloud object storage (Amazon S3, Azure Blob Storage, Google Cloud Storage, etc.).
- **API connectors**: REST clients, SOAP clients, HTTP request components, OData connectors. HTTP-based service integrations.
- **Message queue connectors**: Components for Kafka, RabbitMQ, ActiveMQ, JMS, Azure Service Bus, etc.
- **File transfer connectors**: SFTP, FTP, SCP components for file transfer.
- **Email connectors**: Components for sending/receiving email (SMTP, POP3, IMAP).
- **Shared metadata connections**: Reusable connection configurations defined once and referenced by multiple jobs. They contain host, port, database, schema, username, and (encrypted) password.
- **Connection components**: Components that open a persistent connection at the start of a job, and subsequent read/write components in the same job reuse it via a "use existing connection" setting.

## What to Extract

1. **External system inventory**: For every external system detected, provide:
   - System name (derived from metadata connection name or component configuration)
   - System type (MSSQL, BigQuery, SFTP, REST API, local filesystem, etc.)
   - Connection details: host/endpoint, port, database/dataset name, schema
   - Authentication method: username/password, service account, API key, certificate, OAuth, anonymous
   - Which configuration variables are used for connection parameters
   - Whether the connection is shared (centralized metadata) or inline (per-component)

2. **Usage mapping**: For each external system:
   - Which jobs connect to it
   - What operations are performed (READ, WRITE, READ_WRITE, DELETE)
   - Which specific tables/views/endpoints are accessed
   - Estimated data volume indicators (if queries contain LIMIT, TOP, pagination, or date filters)

3. **Criticality rating**: Rate each external system:
   - **CRITICAL**: Production databases written to, systems where data loss would be severe
   - **HIGH**: Production databases read from, systems feeding downstream processes
   - **MEDIUM**: Staging/temporary storage, logging systems
   - **LOW**: Development/test systems, optional integrations
   - Explain the rationale for each rating

4. **Connection patterns**:
   - Which jobs open their own connections vs. use connections opened by parent jobs?
   - Are there connection pools or shared connections across step groups?
   - Are connections properly closed (look for close/disconnect components in post-job blocks)?

5. **Network topology**: Identify the network flow:
   - Source systems (data originates here)
   - Intermediate systems (staging, temp storage)
   - Target systems (final destination)
   - Direction of data flow between systems

6. **Security observations**:
   - Systems using plaintext credentials vs. encrypted
   - Systems accessible without authentication
   - Systems using hardcoded IPs vs. DNS names
   - Any VPN/tunnel indicators in connection strings

## Instructions

- **Be thorough.** Every database, file path, API endpoint, and external service must be cataloged. Do not miss connections that are configured at the metadata level but not immediately visible in the job definition.
- Trace connection lifecycles -- connections that are opened but never closed are resource leak risks.
- Rate criticality based on the impact of system unavailability and the sensitivity of the data flowing through it.
- Generate a Mermaid topology diagram showing all external systems and the direction of data flow.
- Flag any systems where a single failure would cascade to multiple jobs or regions.
