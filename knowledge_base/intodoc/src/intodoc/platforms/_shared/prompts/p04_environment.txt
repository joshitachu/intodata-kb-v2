You are analyzing an integration project built on a data integration platform. Your task is to produce an **Environment & Configuration Analysis** -- a comprehensive comparison of configuration variables across environments, identification of risky differences, missing values, and hardcoded production credentials or endpoints.

## Integration Platform Context
In integration platforms, environment-specific configuration is managed through **configuration variables** and **environment profiles**:
- **Configuration variables**: Named parameters (e.g., `db_host`, `db_port`, `db_password`) that hold environment-specific values. They are defined at the job level or globally and can be overridden at runtime.
- **Environment profiles**: Named environments such as "Default", "PROD", "TEST", "DEV", "UAT". Each profile provides a different set of values for the same configuration variables. When a job runs, one profile is active.
- **Default profile**: The fallback environment profile. If no environment is specified at runtime, Default values are used. This is risky if Default contains production values.
- **Dynamic configuration loading**: Jobs can load configuration values from files, databases, environment variables, or command-line parameters at runtime, overriding the built-in values.
- **Implicit configuration**: Some platforms support automatic configuration loading at the project level, loading settings from a database table or config service on every job run.
- **Shared configuration**: Configuration defined once and shared across multiple jobs, versus job-specific configuration defined inline.
- **Password/secret fields**: Configuration variables marked as secrets may be stored encrypted in project files but could appear as plaintext in exported archives or properties files.
- **Inline vs shared settings**: Components can use inline settings (hardcoded in the job) or shared/repository references (pointing to centralized metadata). Inline settings are a maintenance risk as they must be updated in every job individually.

## What to Extract

1. **Configuration variable inventory**: For each job, list every configuration variable with its name, type (String, Integer, Password, etc.), and value in each environment profile (Default, PROD, TEST, etc.).

2. **Cross-environment comparison**: For each configuration variable, compare values across all environment profiles. Flag:
   - **Identical values across PROD and TEST**: This suggests the TEST environment may point to production systems (HIGH RISK)
   - **Missing values**: Variables defined but with empty or null values in certain environments
   - **Default = PROD**: Default profile containing production values (RISK: accidental production execution during development)
   - **Hardcoded production URLs/IPs**: Production server addresses, database hosts, or API endpoints embedded directly in component configurations (not via configuration variables)

3. **Password and credential analysis**:
   - Identify all password/secret-type configuration variables
   - Flag any credentials that appear to be in plaintext
   - Identify any hardcoded credentials in inline component configurations
   - Note which jobs handle sensitive credentials

4. **Configuration loading patterns**:
   - Which jobs dynamically load configuration at runtime?
   - What is the source of dynamically loaded configuration (file, database, API, environment variable)?
   - Are there jobs that do NOT load configuration dynamically but should (because they use many configuration variables)?

5. **Inline vs shared settings usage**:
   - For each component using connection parameters, is it inline (hardcoded) or shared (centralized metadata)?
   - Flag inline database connections as a maintenance risk
   - Identify inconsistencies where some components in a job use shared settings and others use inline settings

6. **Environment isolation risks**:
   - Can a TEST run accidentally write to PROD tables based on the configuration?
   - Are there any configuration variables where the PROD and TEST values point to the same server/database?
   - Are there file paths that are environment-specific but hardcoded?

## Instructions

- **Be thorough.** Check every configuration variable in every environment profile. Flag every instance where Default equals PROD. Identify every hardcoded connection parameter.
- Pay special attention to password/secret fields -- even encrypted passwords should be noted, and plaintext passwords are critical findings.
- Inline connection settings are a maintenance debt multiplier -- every job with inline settings is a job that must be individually updated when credentials rotate.
- Environment isolation is a safety-critical concern. If a developer can accidentally execute against production by running with default settings, that is a critical risk.
