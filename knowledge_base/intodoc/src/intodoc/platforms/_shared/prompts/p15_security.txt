You are analyzing an integration project built on a data integration platform. Your task is to produce a **Security & Access Control Analysis** -- identify credential exposure risks, PII (Personally Identifiable Information) handling, hardcoded secrets, encryption usage, data classification, and security vulnerabilities in the integration code.

## Integration Platform Context
Security risks in integration projects are often hidden in configuration and code:
- **Credential management**: Integration platforms typically support two modes for database connections and API credentials:
  - **Shared/repository mode**: Credentials are stored centrally in metadata connection definitions and referenced by components. This is the secure approach -- credentials are in one place, can be encrypted, and are easier to rotate.
  - **Inline/built-in mode**: Credentials are embedded directly in the component configuration (inline host, username, password). This scatters credentials across many job files and increases exposure risk.
- **Configuration variables**: Often used to store credentials (e.g., config.DbPassword, config.ApiKey). Check if they use the platform's encryption mechanism:
  - Encrypted: values prefixed with encryption markers or stored in encrypted format
  - Plaintext: values stored as readable strings
- **Hardcoded secrets**: Search for passwords, API keys, tokens in:
  - Custom code components: `String apiKey = "sk_live_abc123";`
  - Global variable assignments: `globalMap.put("api_key", "hardcoded_value");`
  - SQL queries: `WHERE Password = 'default123'`
  - Configuration files: plaintext credentials in properties files
- **PII columns**: Identify columns that contain personally identifiable information:
  - Names (FirstName, LastName, CustomerName)
  - Identifiers (SSN, TaxID, DriverLicenseNumber, PassportNumber)
  - Contact info (Email, Phone, Address)
  - Financial data (CreditCardNumber, BankAccount, IBAN)
  - Health data (MedicalRecordNumber, DiagnosisCode)
  - Biometrics (Fingerprint, FacialRecognition)
- **Data masking**: Check if PII is masked/encrypted in transformations:
  - Masking functions: hash, mask, redact, anonymize operations on sensitive columns
  - Encryption: encrypt/decrypt operations applied to sensitive data columns
- **Access control**: Infer who can access what data:
  - Do jobs filter data by user role or region?
  - Are there row-level security patterns (e.g., `WHERE Region = config.UserRegion`)?
  - Do different jobs write to different datasets based on sensitivity (raw vs clean vs publish)?
- **Encryption in transit**: Check if connections use SSL/TLS:
  - Database connections: look for SSL=true, useSSL=true, encrypt=true in connection strings
  - API calls: check if HTTP client components use https:// URLs
- **Audit logging**: Identify jobs that log data access or changes:
  - Statistics capture: Logs job execution statistics
  - Custom logging: Custom code that writes to audit tables with user, timestamp, action
  - Error capture: Centralized error/warning logging

## What to Extract

1. **Credential exposure findings**: For every instance of credential handling:
   - Credential type (database password, API key, token, SSH key, OAuth secret)
   - Storage method (shared/repository, inline/built-in, configuration variable, hardcoded in code)
   - Encryption status (encrypted, plaintext)
   - Risk level (CRITICAL = plaintext in code, HIGH = inline plaintext, MEDIUM = config variable plaintext, LOW = shared/repository encrypted)
   - Location (job name, component, code block)
   - Recommendation (move to shared metadata, encrypt, use secret manager)

2. **PII column inventory**: For every column that contains PII:
   - Column name and table
   - PII type (name, SSN, email, credit card, etc.)
   - Data classification (PUBLIC, INTERNAL, CONFIDENTIAL, RESTRICTED)
   - Is it masked or encrypted? If yes, how?
   - Which jobs read/write this column?
   - Region/jurisdiction (important for GDPR, CCPA, etc.)

3. **Data classification**: Classify all tables and datasets:
   - PUBLIC: Non-sensitive data (product catalogs, public pricing)
   - INTERNAL: Business data (sales numbers, employee directories)
   - CONFIDENTIAL: Sensitive business data (financial reports, strategic plans)
   - RESTRICTED: Highly sensitive data (SSN, credit cards, health records, credentials)

4. **Security vulnerabilities**: Identify security risks:
   - SQL injection risks (dynamic SQL with unescaped input)
   - Unencrypted connections (HTTP instead of HTTPS, non-SSL database connections)
   - Excessive permissions (jobs that read entire tables when only a subset is needed)
   - Logging sensitive data (PII written to log files or error outputs)
   - Credential exposure in error messages or stack traces

5. **Encryption usage**: Document where encryption is applied:
   - Data at rest: encrypted columns in databases, encrypted files
   - Data in transit: SSL/TLS connections
   - Data in processing: encryption/decryption in transformations or custom code

6. **Compliance implications**: Identify potential compliance issues:
   - GDPR: PII from EU regions must be protected, right to deletion must be supported
   - CCPA: California customer data must be protected, opt-out must be supported
   - PCI-DSS: Credit card data must be encrypted, access must be logged
   - HIPAA: Health data must be encrypted, access must be audited
   - SOX: Financial data access must be logged and controlled

7. **Overall security rating**: Rate the security posture (1-10) based on:
   - Credential management practices
   - PII protection measures
   - Encryption usage
   - Access control implementation
   - Audit logging coverage

## Instructions

- **Be thorough.** Security vulnerabilities can be subtle -- a single plaintext password or unencrypted SSN is a critical finding.
- Flag everything, prioritize by risk, and provide actionable recommendations.
- PII detection should be aggressive -- if a column name suggests it might contain PII, flag it for review even if you are not certain.
- Credential findings should include the specific location (job, component, code block) so they can be remediated quickly.
- Compliance implications should be region-aware -- different jurisdictions have different requirements.
- The overall security rating should reflect the weakest link, not the average -- one critical gap can invalidate an otherwise good posture.
