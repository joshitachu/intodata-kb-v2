You are analyzing an integration project built on a data integration platform. Your task is to produce a **Schema & Data Dictionary** -- a comprehensive catalog of every table, view, and column definition flowing through the integration, extracted from metadata connections, transformation output schemas, component schemas, and SQL queries.

## Integration Platform Context
In integration platforms, schema information is scattered across multiple locations:
- **Metadata connections** (connection definition files): These define database connections and often include table/view schemas with column definitions (name, type, length, nullable, key constraints). Look for column definitions with name, source type, data type, length, precision, nullable, and key attributes.
- **Transformation output schemas**: Each transformation output has a schema section defining the columns it produces. These columns may be mapped from input schemas or computed via expressions.
- **Component connection schemas**: Every data flow connection between components carries a schema. These can be inline (column elements in the connection definition) or referenced from shared/repository metadata.
- **Source component schemas**: Database reader, API reader, and file reader components have schemas that define what columns are read from the source. If they reference a view or table, the schema should match the metadata definition.
- **Sink component schemas**: Database writer, file writer, and cloud storage writer components have schemas that define what columns are written to the target.
- **SQL queries**: SELECT statements embedded in source components reveal which columns are actually used, and may include derived columns (aliases, CAST, CASE expressions).
- **Schema evolution**: As data flows through transformations, schemas evolve -- columns are added, renamed, cast to different types, or dropped.

## What to Extract

1. **Tables and views catalog**: For every database table, view, or file schema referenced in the project:
   - Table/view name (fully qualified: database.schema.table)
   - Source system (MSSQL, BigQuery, Oracle, File, etc.)
   - Schema definition: all columns with name, data type, length/precision/scale, nullable, primary key, foreign key
   - Whether it is a source (read from), target (written to), or both
   - Which jobs read from or write to it
   - Any SQL query customizations (filtered columns, computed columns)

2. **Schema transformations**: For each job, trace how the schema changes from input to output:
   - Input schema (source columns)
   - Transformation steps (mapping adds/renames/casts columns, aggregation reduces and summarizes, custom code may add computed columns)
   - Output schema (target columns)

3. **Unmapped columns**: Identify columns that exist in source schemas but are never used downstream, or columns that exist in target schemas but have no clear source.

4. **Data type mismatches**: Identify cases where a column's data type changes between source and target (e.g., String -> Integer, Date -> String, Decimal -> Float) -- these may indicate risk of data loss or conversion errors.

5. **Schema inconsistencies**: Identify cases where the same logical entity (e.g., "Customer") has different schemas in different jobs or regions (different column names, different types, missing columns).

6. **Entity-relationship diagram**: Infer relationships between tables based on:
   - Lookup joins in transformations (join keys suggest foreign key relationships)
   - Column name patterns (columns named customer_id, order_id suggest relationships)
   - SQL JOIN clauses in source queries

## Instructions

- **Be thorough.** Document every table, every column, every schema transformation. If a column's purpose is unclear, say so.
- Schema inconsistencies between regions or domains are critical findings -- they often indicate bugs or compatibility issues that will surface during data consolidation.
- Data type mismatches should be rated by risk level. Widening conversions (int -> bigint) are low risk. Narrowing conversions (decimal -> int, long string -> short string) are high risk.
- Unmapped columns are important to flag -- they may indicate unused data (waste) or missing transformations (bugs).
- Generate an ER diagram in Mermaid format showing inferred relationships between key tables.
