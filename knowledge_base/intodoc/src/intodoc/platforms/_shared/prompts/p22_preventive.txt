You are analyzing an integration project built on a data integration platform. Your task is to produce a **Preventive Analysis** -- a forward-looking assessment that predicts what will go wrong next, identifies missing safeguards, catalogs anti-patterns, scores job fragility, and provides health score inputs for a composite project health metric.

This is NOT a description of current issues (that is covered by error handling and known issues passes). This pass focuses on **latent risks that have not yet manifested**, **missing safeguards that should exist**, and **anti-patterns that will cause future failures**.

## Integration Platform Context

### Anti-Patterns to Detect

- **DELETE-INSERT without guards**: A DELETE or TRUNCATE operation followed by an INSERT with no row-count validation, no transaction wrapping, and no rollback. If INSERT fails after DELETE, the target table is empty until the next successful run.
- **Error-masking try-catch**: Custom code loops (e.g., pagination, API polling) that catch all exceptions and print a success message -- masks API errors, timeouts, and partial extractions as successful completions.
- **Child error propagation disabled without checking**: Orchestration calls where child failures are silently ignored and the parent continues processing stale or missing data.
- **TRUNCATE without row count validation**: Write mode TRUNCATE on target tables with no pre/post row count comparison. Zero-row writes after truncation go undetected.
- **Copy/backup jobs in production paths**: Jobs with "Copy_of_", "_Backup", "_OLD", "_TEST" suffixes that may be accidentally scheduled or called by orchestrators instead of the canonical version.
- **Unbounded queries**: Extractions with no WHERE clause, no date filter, no pagination, and no row limit -- vulnerable to data volume growth causing timeouts or memory exhaustion.
- **Hardcoded environment values**: Dataset names, server addresses, fiscal years, or API endpoints embedded in job logic instead of configuration variables.

### Missing Safeguards to Catalog

- **No centralized error logging**: Jobs without error capture components -- failures produce no audit trail.
- **No retry logic**: API extractions (REST, SOAP, OData) with no retry on transient failures (timeouts, rate limits, 5xx errors).
- **No alerting mechanism**: No email notification, no webhook, no external alert on failure -- failures are only detected when downstream consumers notice stale data.
- **No data freshness checks**: No comparison of extraction timestamps, no "last successful run" tracking, no staleness detection.
- **No referential integrity validation**: JOIN operations with no check for orphaned or unmatched records -- silently drops rows.
- **No idempotency**: Jobs that cannot be safely re-run without side effects (double-counting, duplicate inserts, re-deletion).
- **No graceful degradation**: No fallback behavior when upstream dependencies fail -- entire pipeline halts or produces corrupt output.

### Fragile Patterns to Flag

- **Hardcoded fiscal years**: SQL queries or transformation expressions with literal year values (e.g., '2023/2024') that must be manually updated each cycle.
- **Sentinel dates**: Magic date values used as "no date" markers (e.g., '1900-01-01', '9999-12-31') that may conflict with real data.
- **Fixed dataset references**: Target dataset or schema names hardcoded in SQL instead of parameterized via configuration variables.
- **Version proliferation**: Jobs with 5+ versions (v1, v2, ..., v15) where the canonical version is unclear.
- **Credential files on disk**: API keys, OAuth tokens, or passwords loaded from flat files with no encryption at rest.

### Single Points of Failure

- **Shared reference tables**: Tables consumed by many jobs across regions (e.g., account mappings, fiscal periods) where corruption cascades everywhere.
- **Single orchestrator**: One parent job controlling all child jobs with no fallback if the orchestrator itself fails.
- **Single source connection**: All extractions for a region depending on one database connection or one API endpoint.

### Implicit Assumptions

- **Upstream data always exists**: Jobs that read from tables written by other jobs with no check that the upstream job ran successfully.
- **Schema never changes**: Column lists hardcoded in SELECT statements or transformation mappings with no schema drift detection.
- **API contracts are stable**: REST/SOAP endpoints assumed to maintain backward compatibility with no version pinning.
- **Execution order is guaranteed**: Jobs that depend on sequence but have no explicit orchestration enforcing it.

## What to Extract

### 1. Latent Failure Scenarios

For each identified scenario where a failure COULD occur but has not been explicitly handled:

- **trigger**: What event or condition would cause this failure
- **impact**: What happens when it fails (data loss, stale data, corrupt data, silent error)
- **probability**: HIGH / MEDIUM / LOW (based on how common the trigger is)
- **detection_difficulty**: EASY / MODERATE / HARD / UNDETECTABLE (how long before someone notices)
- **affected_jobs**: List of job names
- **proposed_fix**: Specific remediation (not generic advice)

### 2. Missing Safeguard Catalog

For each missing safeguard:

- **safeguard**: What should exist (e.g., "centralized error logging for audit trail")
- **protects_against**: What failure mode it prevents
- **affected_jobs**: Jobs missing this safeguard
- **effort_to_add**: TRIVIAL (< 1 hour) / SMALL (1-4 hours) / MEDIUM (1-2 days) / LARGE (1 week+)

### 3. Anti-Pattern Instances

For each detected anti-pattern:

- **pattern**: Which anti-pattern from the list above (or a new one you identify)
- **location**: Job name and component
- **specific_risk**: What exactly could go wrong in THIS instance
- **proposed_fix**: How to remediate

### 4. Fragility Score per Job

Rate every job on a 4-point scale:

- **BRITTLE**: Multiple anti-patterns, no error handling, hardcoded values, no safeguards. Will break under any change.
- **FRAGILE**: Some anti-patterns or missing safeguards. Likely to break under moderate change.
- **ADEQUATE**: Basic error handling present, no critical anti-patterns. Handles expected failures.
- **ROBUST**: Comprehensive error handling, retry logic, validation, parameterized. Handles unexpected failures gracefully.

### 5. Technical Debt Indicators

- **copy_variants**: Jobs with Copy_of_, _Backup, _DEBUG, _COPY, _POC, _Test prefixes/suffixes
- **version_proliferation**: Jobs where the highest version number suggests many iterations (v5+)
- **hardcoded_values**: Count of hardcoded dataset names, server addresses, fiscal years
- **code_duplication**: Groups of near-identical jobs that should share a template or common routine
- **missing_cleanup**: Deprecated jobs that are never called but still exist in the project

### 6. Cascading Failure Chains

Trace failure propagation paths:

- **source**: The initial failure point (job + component)
- **propagation**: How the failure spreads (via orchestration, shared tables, reference data)
- **blast_radius**: CRITICAL (affects all regions) / HIGH (affects multiple regions) / MEDIUM (affects one region) / LOW (affects one job)

### 7. Health Score Inputs

Calculate percentage scores for these dimensions (0-100):

- **error_handling_pct**: % of jobs with at least one error handling mechanism (abort/die, centralized error capture, failure triggers, try-catch)
- **data_integrity_pct**: % of write operations with guards (row count validation, transaction wrapping, rollback config)
- **code_hygiene_pct**: % of jobs that are NOT copy/backup/debug/test variants
- **observability_pct**: % of jobs with logging or monitoring (error capture, statistics capture, logging on error paths)

## Instructions

- **Be thorough and forward-looking.** Focus on what WILL go wrong, not what HAS gone wrong.
- Every identified risk should have a specific, actionable fix -- not generic advice like "add error handling." Name specific jobs, components, and scenarios.
- Latent failures are the highest-value findings -- these are problems waiting to happen. Rate them by both probability and detection difficulty.
- Health scores should be calculated from actual job counts, not estimated. If 3 out of 20 jobs have error handling, error_handling_pct = 15.
- Technical debt indicators help quantify the maintenance burden. Copy variants and version proliferation are strong signals of accumulated debt.
- Cascading failure chains are critical findings -- trace the full blast radius from initial failure to final impact.
