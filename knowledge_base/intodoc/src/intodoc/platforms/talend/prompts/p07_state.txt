You are analyzing a Talend integration project. Your task is to produce a **State & Side Effects Analysis** — a thorough identification of every temporary file, staging table, global variable, and persistent side effect produced by the jobs in this chunk, including cleanup gaps that could cause issues on re-runs or failures.

## Talend Context
Talend jobs can create various forms of state and side effects that persist beyond the job's execution:
- **Temporary files**: Jobs often write intermediate data to local or network files (tFileOutputDelimited, tFileOutputExcel) during processing. These should be cleaned up in tPostJob but often are not.
- **Staging tables**: Jobs may write to intermediate/staging database tables (e.g., `stg_*`, `tmp_*`, `_temp_*`) that are used by subsequent jobs. These need to be truncated or dropped after use.
- **Global variables**: Talend components expose globalMap variables (e.g., `((Integer)globalMap.get("tMSSqlInput_1_NB_LINE"))`) that hold row counts, error counts, file paths, and other runtime state. These persist within a job execution and can be passed between tRunJob calls.
- **Context variables modified at runtime**: Jobs can modify context variables during execution using tContextLoad or tSetGlobalVar. These modified values can persist if passed to child jobs.
- **tSetGlobalVar**: Explicitly sets a globalMap variable to a value, which subsequent components can reference.
- **Buffer files**: tMap, tSortRow, tAggregateRow and other components may create temporary buffer files on disk for large datasets. These are usually auto-cleaned but can be orphaned if the job crashes.
- **Database locks**: Long-running transactions can hold locks on tables. If a job fails mid-transaction without rollback, locks may persist.
- **File locks**: Jobs that open files for writing may hold file locks. If the job crashes, these locks may persist on Windows systems.
- **tCreateTemporaryFile**: Explicitly creates a temp file that should be cleaned up later.
- **cleanup_temp_file_storage**: A Talend utility method/pattern for cleaning up temporary files at the end of a job. Check if it is present in tPostJob or tFinally blocks.
- **tFileDelete**: Component that deletes files. Should be present in tPostJob to clean up temp files.
- **State in external systems**: Jobs may create/modify state in external systems (e.g., updating a "last_sync_date" column, setting status flags, creating audit log entries) that persist after the job completes.

## What to Extract

1. **Temporary files**: For each job, identify:
   - Every file write operation (tFileOutputDelimited, tFileOutputExcel, tFileOutputJSON, etc.)
   - The file path (is it hardcoded or from a context variable?)
   - Whether the file is cleaned up after use (look for tFileDelete in tPostJob)
   - What happens to the file if the job fails mid-execution

2. **Staging tables**: Identify:
   - Database tables that appear to be temporary/staging (naming conventions: stg_, tmp_, temp_, _staging, _buffer)
   - Tables that are truncated at the start of a job (indicating they are staging)
   - Tables written to in one job and read from in another (cross-job dependencies)
   - Whether staging tables are cleaned up after the data is consumed

3. **Global variables (globalMap)**: For each job:
   - Which globalMap variables are SET (via tSetGlobalVar, tFlowToIterate, or component outputs)
   - Which globalMap variables are READ by subsequent components
   - Which globalMap variables are passed to child jobs via tRunJob
   - Any globalMap variables that control execution flow (used in RunIf conditions or tJava if-statements)

4. **Context variable mutations**: Identify:
   - Jobs that modify context variables at runtime (tContextLoad, tSetGlobalVar with context.*)
   - Whether these mutations affect child jobs called later
   - Whether the mutations are documented or commented

5. **Cleanup analysis**: For each job:
   - Does tPostJob exist? What cleanup operations does it perform?
   - Does tPostJob run on BOTH success and failure? (tPostJob always runs unless the JVM crashes)
   - Are there cleanup gaps — files or tables created but never cleaned up?
   - Is cleanup_temp_file_storage called?

6. **Persistent side effects**: Identify all changes that persist in external systems after the job completes:
   - Database rows inserted/updated/deleted
   - Files created on file systems
   - Audit log entries created
   - Status flags or watermark values updated (e.g., "last_processed_date")
   - Email notifications sent

7. **Re-run safety**: Assess what happens if each job is run twice:
   - Are writes idempotent (e.g., TRUNCATE before INSERT, or UPSERT)?
   - Could a re-run cause duplicate data?
   - Could a re-run fail because temp files already exist or staging tables have stale data?
