You are analyzing a Talend integration project. Your task is to produce a **Security & Access Control Analysis** — identify credential exposure risks, PII (Personally Identifiable Information) handling, hardcoded secrets, encryption usage, data classification, and security vulnerabilities in the integration code.

## Talend Context
Security risks in Talend projects are often hidden in configuration and code:
- **Credential management**: Talend supports two modes for database connections and API credentials:
  - **REPOSITORY mode**: Credentials are stored centrally in metadata/connections/*.item files and referenced by components. This is the secure approach — credentials are in one place, can be encrypted, and are easier to rotate.
  - **BUILT_IN mode**: Credentials are embedded directly in the component configuration (inline host, username, password). This scatters credentials across many .item files and increases exposure risk.
  - Look for `<elementParameter name="PROPERTY:PROPERTY_TYPE" value="REPOSITORY">` vs `<elementParameter name="PROPERTY:PROPERTY_TYPE" value="BUILT_IN">`
- **Context variables**: Often used to store credentials (context.DbPassword, context.ApiKey). Check if they use Talend's encryption mechanism:
  - Encrypted: `<elementParameter name="VALUE" value="enc:system.encryption.key.v1,base64encodedvalue">`
  - Plaintext: `<elementParameter name="VALUE" value="mypassword123">`
- **Hardcoded secrets**: Search for passwords, API keys, tokens in:
  - tJava/tJavaRow code: `String apiKey = "sk_live_abc123";`
  - tSetGlobalVar: `globalMap.put("api_key", "hardcoded_value");`
  - SQL queries: `WHERE Password = 'default123'`
- **PII columns**: Identify columns that contain personally identifiable information:
  - Names (FirstName, LastName, CustomerName)
  - Identifiers (SSN, TaxID, DriverLicenseNumber, PassportNumber)
  - Contact info (Email, Phone, Address)
  - Financial data (CreditCardNumber, BankAccount)
  - Health data (MedicalRecordNumber, DiagnosisCode)
  - Biometrics (Fingerprint, FacialRecognition)
- **Data masking**: Check if PII is masked/encrypted in transformations:
  - Masking functions: `Routines.DataMasking.maskSSN(row1.SSN)`, `StringHandling.EREPLACE(row1.Email, "@.*", "@masked.com", 0)`
  - Encryption: `Routines.Encryption.encrypt(row1.CreditCardNumber, context.EncryptionKey)`
- **Access control**: Infer who can access what data:
  - Do jobs filter data by user role or region?
  - Are there row-level security patterns (e.g., `WHERE Region = context.UserRegion`)?
  - Do different jobs write to different datasets based on sensitivity (raw vs clean vs publish)?
- **Encryption in transit**: Check if connections use SSL/TLS:
  - Database connections: look for `SSL=true` or `useSSL=true` in connection strings
  - API calls: check if tRESTClient URLs use https://
- **Audit logging**: Identify jobs that log data access or changes:
  - tStatCatcher: Logs job execution statistics
  - Custom logging: tJava writes to audit tables with user, timestamp, action
  - tLogCatcher: Captures errors and warnings

## What to Extract

1. **Credential exposure findings**: For every instance of credential handling:
   - Credential type (database password, API key, token, SSH key)
   - Storage method (REPOSITORY, BUILT_IN, context variable, hardcoded)
   - Encryption status (encrypted, plaintext)
   - Risk level (CRITICAL = plaintext in code, HIGH = BUILT_IN plaintext, MEDIUM = context plaintext, LOW = REPOSITORY encrypted)
   - Location (job name, component, line of code)
   - Recommendation (move to REPOSITORY, encrypt, use secret manager)

2. **PII column inventory**: For every column that contains PII:
   - Column name and table
   - PII type (name, SSN, email, credit card, etc.)
   - Data classification (PUBLIC, INTERNAL, CONFIDENTIAL, RESTRICTED)
   - Is it masked or encrypted? If yes, how?
   - Which jobs read/write this column?
   - Region/jurisdiction (important for GDPR, CCPA, etc.)

3. **Data classification**: Classify all tables and datasets:
   - PUBLIC: Non-sensitive data (product catalogs, public pricing)
   - INTERNAL: Business data (sales numbers, employee directories)
   - CONFIDENTIAL: Sensitive business data (financial reports, strategic plans)
   - RESTRICTED: Highly sensitive data (SSN, credit cards, health records, credentials)

4. **Security vulnerabilities**: Identify security risks:
   - SQL injection risks (dynamic SQL with unescaped user input)
   - Unencrypted connections (HTTP instead of HTTPS, non-SSL database connections)
   - Excessive permissions (jobs that read entire tables when only a subset is needed)
   - Logging sensitive data (PII written to log files or error outputs)

5. **Encryption usage**: Document where encryption is applied:
   - Data at rest: encrypted columns in databases, encrypted files
   - Data in transit: SSL/TLS connections
   - Data in processing: encryption/decryption in tMap or Java routines

6. **Compliance implications**: Identify potential compliance issues:
   - GDPR: PII from EU regions must be protected, right to deletion must be supported
   - CCPA: California customer data must be protected, opt-out must be supported
   - PCI-DSS: Credit card data must be encrypted, access must be logged
   - HIPAA: Health data must be encrypted, access must be audited

7. **Overall security rating**: Rate the security posture (1-10) based on:
   - Credential management practices
   - PII protection measures
   - Encryption usage
   - Access control implementation
   - Audit logging coverage
