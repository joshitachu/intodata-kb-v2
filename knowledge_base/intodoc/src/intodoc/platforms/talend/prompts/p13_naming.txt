You are analyzing a Talend integration project. Your task is to produce a **Naming Conventions Analysis** — decode and document the naming patterns used for jobs, components, tables, columns, context variables, and metadata connections. For Vaxxinova specifically, decode the standard pattern: `{REGION}_{SUBSIDIARY}_{LAYER}_{VERSION}`.

## Talend Context
Naming conventions in Talend integration projects serve as embedded documentation. Consistent naming makes the codebase self-documenting and reveals:
- **Organizational structure**: Region codes (BRA, ITA, JPN, SAF, USA) and subsidiary codes (VBR, VAX, VJP, VSA, NPL) encode which business unit owns the data
- **Data layer architecture**: Layer codes (RAW, CLEAN, PUBLISH, STAGING) reveal the data transformation pipeline structure
- **Job purpose**: Job names encode what the job does and where it sits in the pipeline
- **Versioning**: Version suffixes (_0.1, _v2) indicate job evolution
- **Component naming**: Components within a job may follow patterns like `tMSSqlInput_SourceName`, `tMap_TransformLogic`, `tBigQueryOutput_TargetTable`
- **Metadata naming**: Connection names often encode environment (PROD, TEST) and system (MSSQL_BRA_VBR, BQ_PROJECT_DATASET)
- **Context variable naming**: Variables follow patterns like `{REGION}_{SUBSIDIARY}_{PARAMETER}` (e.g., `BRA_VBR_Host`, `USA_NPL_Database`)

## Vaxxinova-Specific Patterns
Based on the Vaxxinova integration project, the standard job naming pattern is:
**`{REGION}_{SUBSIDIARY}_{LAYER}_{VERSION}`**

### Region Codes
- **BRA** = Brazil
- **ITA** = Italy
- **JPN** = Japan
- **SAF** = South Africa
- **USA** = United States

### Subsidiary Codes
- **VBR** = Vaxxinova Brazil
- **VAX** = Vaxxinova Italy
- **VJP** = Vaxxinova Japan
- **VSA** = Vaxxinova South Africa
- **NPL** = Newport Labs (USA subsidiary)

### Layer Codes
- **RAW** = Source extract layer — reads data from source systems with minimal transformation, preserves source format
- **CLEAN** = Data cleansing and transformation layer — applies validation, standardization, enrichment
- **PUBLISH** = Final output layer — produces analytics-ready tables with business-friendly schemas
- **STAGING** = Temporary intermediate layer (if used)
- **GLOBAL** = Cross-region orchestration jobs that call multiple regional jobs

### Version Pattern
- **_0.1**, **_v1**, **_v2** = Version suffixes indicating job iterations

### Examples
- `BRA_VBR_RAW_0.1` = Brazil, Vaxxinova Brazil subsidiary, RAW layer, version 0.1
- `USA_NPL_CLEAN_0.1` = United States, Newport Labs subsidiary, CLEAN layer, version 0.1
- `GLOBAL_Orchestrator_0.1` = Cross-region orchestration job, version 0.1

## What to Extract

1. **Detected naming patterns**: For each category (jobs, components, tables, columns, metadata, context variables), identify:
   - The naming pattern template
   - Pattern elements (prefix, suffix, separators, codes)
   - Examples of names that follow the pattern
   - Pattern adherence rate (what % of names follow the pattern?)

2. **Region/Subsidiary/Layer usage**: For the Vaxxinova pattern:
   - List all region codes found and their decoded meanings
   - List all subsidiary codes found and their decoded meanings
   - List all layer codes found and their decoded meanings
   - Identify any codes that don't match the known set (e.g., "GER" for Germany if it appears)

3. **Naming violations**: Identify names that deviate from the expected pattern:
   - Jobs that don't follow `{REGION}_{SUBSIDIARY}_{LAYER}_{VERSION}`
   - Inconsistent separators (underscores vs camelCase vs spaces)
   - Missing elements (no region, no layer, no version)
   - Ambiguous abbreviations (is "BRA" a region or a data source name?)
   - Generic names (job_1, tMap_2, connection_1) that provide no semantic meaning

4. **Abbreviation glossary**: Decode all abbreviations found:
   - Region/subsidiary/layer codes (already listed above)
   - Domain-specific abbreviations in table/column names (e.g., "VW_" for view, "TEMP_" for temporary)
   - Common suffixes (e.g., "_ID" for identifiers, "_DT" for dates, "_AMT" for amounts)

5. **Consistency analysis**: Measure consistency across the project:
   - Are region codes always uppercase? Are separators always underscores?
   - Do all jobs in the same layer use the same layer code, or is there variation (CLEAN vs Clean vs clean)?
   - Are versioning conventions consistent (_0.1 vs _v1 vs no version)?
   - Do component names within a job follow a pattern, or are they arbitrary (tMSSqlInput_1 vs tMSSqlInput_Source)?

6. **Naming recommendations**: Suggest improvements:
   - Standardize deviations to match the primary pattern
   - Replace generic names with descriptive names
   - Document any intentional exceptions (e.g., GLOBAL jobs don't have a region code by design)
