You are analyzing a Talend integration project. Your task is to produce a **Schema & Data Dictionary** — a comprehensive catalog of every table, view, and column definition flowing through the integration, extracted from metadata connections, tMap output schemas, component schemas, and SQL queries.

## Talend Context
In Talend, schema information is scattered across multiple locations:
- **Metadata connections** (*.item files in metadata/connections/): These define database connections and often include table/view schemas with column definitions (name, type, length, nullable, key constraints). Look for `<column>` tags with `name`, `sourceType`, `type`, `length`, `precision`, `nullable`, `key` attributes.
- **tMap output schemas**: Each tMap outputTable has a schema section defining the columns it produces. These columns may be mapped from input schemas or computed via expressions.
- **Component connection schemas**: Every FLOW connection between components carries a schema. These can be inline (`<column>` elements in the connection definition) or referenced from REPOSITORY metadata (`<elementParameter name="SCHEMA" field="SCHEMA_TYPE" value="REPOSITORY">`).
- **Source component schemas**: tMSSqlInput, tBigQueryInput, etc. have schemas that define what columns are read from the source. If they reference a view or table, the schema should match the metadata definition.
- **Sink component schemas**: tMSSqlOutput, tBigQueryOutput, etc. have schemas that define what columns are written to the target.
- **SQL queries**: SELECT statements embedded in source components reveal which columns are actually used, and may include derived columns (aliases, CAST, CASE expressions).
- **Schema evolution**: As data flows through transformations, schemas evolve — columns are added, renamed, cast to different types, or dropped.

## What to Extract

1. **Tables and views catalog**: For every database table, view, or file schema referenced in the project:
   - Table/view name (fully qualified: database.schema.table)
   - Source system (MSSQL, BigQuery, Oracle, File, etc.)
   - Schema definition: all columns with name, data type, length/precision/scale, nullable, primary key, foreign key
   - Whether it's a source (read from), target (written to), or both
   - Which jobs read from or write to it
   - Any SQL query customizations (filtered columns, computed columns)

2. **Schema transformations**: For each job, trace how the schema changes from input to output:
   - Input schema (source columns)
   - Transformation steps (tMap adds/renames/casts columns, tAggregateRow reduces and aggregates, tJavaRow may add computed columns)
   - Output schema (target columns)

3. **Unmapped columns**: Identify columns that exist in source schemas but are never used downstream, or columns that exist in target schemas but have no clear source.

4. **Data type mismatches**: Identify cases where a column's data type changes between source and target (e.g., String -> Integer, Date -> String, BigDecimal -> Float) — these may indicate risk of data loss or conversion errors.

5. **Schema inconsistencies**: Identify cases where the same logical entity (e.g., "Customer") has different schemas in different jobs or regions (different column names, different types, missing columns).

6. **Entity-relationship diagram**: Infer relationships between tables based on:
   - Lookup joins in tMap (join keys suggest foreign key relationships)
   - Column name patterns (columns named customer_id, order_id suggest relationships)
   - SQL JOIN clauses in source queries
