You are analyzing a Talend integration project. Your task is to produce a **Performance Profile** — identify performance bottlenecks, optimization opportunities, and resource-intensive operations based on job structure, component configuration, data volumes, and transformation complexity.

## Talend Context
Performance in Talend is influenced by many factors, and optimization opportunities are often hidden in component properties:
- **Database I/O settings**: Key properties that affect performance:
  - **BATCH_SIZE** / **COMMIT_EVERY** on DB output components: larger batches reduce commit overhead (default is often 10K, but 50K-100K may be faster)
  - **FETCH_SIZE** on DB input components: controls how many rows are fetched per roundtrip (default 100, but 1000-10000 may be faster for large datasets)
  - **USE_BATCH** on DB outputs: enables batch mode (faster than row-by-row inserts)
  - **ENABLE_DEBUG_MODE**: if set to true, logs every row — massive performance hit, should be false in production
- **tMap configuration**: Performance killers in tMap:
  - **lookupMode = LOAD_ONCE**: loads entire lookup table into memory — fast for small lookups, but causes OutOfMemoryError for large lookups (>1M rows)
  - **lookupMode = RELOAD**: re-queries database for each input row — slow but memory-safe
  - **matchingMode = ALL_MATCHES**: creates Cartesian product if lookup returns multiple matches — can explode memory and processing time
  - **matchingMode = UNIQUE_MATCH**: expects 1:1 match — fails if multiple matches found
  - **tMap expression complexity**: complex Java expressions in every output column can be CPU-intensive
- **tSortRow**: Sorts data in memory — extremely slow for large datasets (>1M rows). Should be replaced with database-side ORDER BY when possible.
- **tAggregateRow**: Aggregates data in memory — same performance issue as tSortRow for large datasets. Push to database (SQL GROUP BY) when possible.
- **tJavaRow**: Row-by-row Java transformation — overhead for function calls on every row. Consider bulk operations or tMap instead.
- **tUnite**: Combines multiple flows — no performance impact (just merges streams)
- **tDenormalize/tNormalize**: Memory-intensive structural transformations
- **File I/O**: Large file processing can be slow:
  - **tFileInputDelimited** with large files (>1GB): consider splitting files or using parallel processing
  - **tFileOutputDelimited** with APPEND mode: faster than recreating file each time
- **Network latency**: Remote database connections and API calls add latency:
  - Minimize roundtrips by batching
  - Use bulk operations (BULK_INSERT, COPY, batch API calls) instead of row-by-row
- **Parallelization**: Subjobs connected with onComponentOk run in parallel — use this to parallelize independent operations
- **Data volume indicators**: Infer data volume from:
  - Table names (FACT tables = large, DIM tables = small)
  - Comments in SQL queries ("fetches ~2M rows daily")
  - tMap lookup warnings ("lookup table has 5M rows")

## What to Extract

1. **Performance profile for each job**: For every job:
   - Estimated row count (small <10K, medium 10K-1M, large 1M-10M, very large >10M)
   - Heavy operations (tSortRow, tAggregateRow, LOAD_ONCE lookups on large tables, complex tMap expressions)
   - Batch size settings (COMMIT_EVERY, FETCH_SIZE, BATCH_SIZE)
   - Performance risks (operations that may become bottlenecks as data grows)
   - Estimated execution time (fast <1 min, medium 1-10 min, slow 10-60 min, very slow >60 min)

2. **Optimization opportunities**: For each performance issue:
   - Current implementation (what the job does now)
   - Performance issue (why it's slow or inefficient)
   - Recommended optimization (how to make it faster)
   - Expected impact (how much faster it could be)
   - Effort to implement (low, medium, high)

3. **Memory-intensive operations**: Identify jobs that may run out of memory:
   - tMap with LOAD_ONCE on large lookup tables
   - tSortRow on large datasets
   - tAggregateRow with many groups
   - tMap with ALL_MATCHES join on tables with duplicates

4. **Slow job candidates**: Rank jobs by estimated execution time and performance risk:
   - Which jobs are likely to be the slowest?
   - Which jobs will degrade as data volume grows?
   - Which jobs should be optimized first?

5. **Batch size analysis**: For all database output components:
   - Current batch size (COMMIT_EVERY, BATCH_SIZE)
   - Recommended batch size (based on data volume and database type)
   - Whether USE_BATCH is enabled

6. **Database pushdown opportunities**: Identify transformations done in Talend that could be pushed to the database:
   - tMap joins -> SQL JOIN in source query
   - tSortRow -> ORDER BY in source query
   - tAggregateRow -> GROUP BY in source query
   - tFilterRow -> WHERE clause in source query
   - tMap expressions -> computed columns in source query (CASE, CAST, string functions)

7. **Overall performance rating**: Rate the performance optimization level (1-10) based on:
   - Batch size configuration
   - Use of database pushdown
   - Avoidance of memory-intensive operations
   - Parallelization usage
