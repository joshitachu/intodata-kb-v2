You are analyzing a Talend integration project. Your task is to produce a **Data Quality & Validation Analysis** — a comprehensive catalog of all validation rules, null handling patterns, data quality checks, and data cleansing logic embedded in the integration.

## Talend Context
Data quality logic in Talend is implemented across multiple components and patterns:
- **tMap expressions**: The primary location for data cleansing and validation. Look for:
  - Null checks: `row1.field == null ? defaultValue : row1.field` or `row1.field != null ? row1.field : 0`
  - String trimming: `StringHandling.TRIM(row1.field)` removes leading/trailing whitespace
  - String casing: `StringHandling.UPCASE()` or `StringHandling.DOWNCASE()` for standardization
  - Type coercion: `Integer.parseInt(row1.field)`, `new BigDecimal(row1.field)`, `TalendDate.parseDate()`
  - Default values: expressions that replace missing/invalid data with defaults
  - Data cleansing: `StringHandling.EREPLACE(row1.field, "[^a-zA-Z0-9]", "", 0)` removes special characters
  - Length truncation: `row1.field.substring(0, 50)` enforces field length limits
- **tMap filter expressions**: Row-level validation that rejects invalid rows. Look for:
  - Range checks: `row1.Amount > 0 && row1.Amount < 1000000`
  - Mandatory field checks: `row1.CustomerID != null && !row1.CustomerID.isEmpty()`
  - Pattern validation: `row1.Email.matches(".*@.*\\..*")`
  - Date range validation: `row1.OrderDate.after(minDate) && row1.OrderDate.before(maxDate)`
- **tFilterRow**: Explicit filtering component with conditions that validate data and route valid/invalid rows to different outputs
- **tSchemaComplianceCheck**: Validates that incoming data matches expected schema (data types, nullability, length)
- **tAssert**: Component that enforces assertions — job fails if the assertion is false (e.g., "COUNT(*) must be > 0")
- **SQL validation**: WHERE clauses in source queries that filter out invalid data at the source (e.g., `WHERE IsDeleted = 0 AND Status IN ('A','P')`)
- **Java routines**: Custom validation functions like `Routines.DataValidation.isValidEmail(String)`, `Routines.DataCleansing.cleanPhoneNumber(String)`
- **tJavaRow/tJava**: Inline Java code that performs complex validation or data cleansing
- **Reject links**: tMap reject outputs route rows that fail lookup joins or filters — these rejected rows are often logged or written to error tables

## What to Extract

1. **Validation rules**: For every validation check in the code:
   - Rule ID (unique identifier)
   - Job and component where the rule is implemented
   - Rule type (null_check, range_check, format_validation, mandatory_field, type_validation, referential_integrity, etc.)
   - Rule description in plain English
   - Expression or condition that implements the rule
   - Severity (CRITICAL = job should fail, HIGH = row rejected, MEDIUM = warning logged, LOW = default value applied)
   - Action taken when validation fails (reject row, log warning, apply default, halt job)

2. **Null handling patterns**: For every column, document how null values are handled:
   - Is null allowed?
   - If null is not allowed, what happens? (reject row, replace with default, fail job)
   - What default value is used?
   - Is the default value business-meaningful or a technical placeholder (e.g., "N/A", "UNKNOWN", 0, empty string)?

3. **Data cleansing transformations**: For every data cleansing operation:
   - Column affected
   - Cleansing operation (trim, uppercase, remove special characters, truncate, standardize format, etc.)
   - Reason for cleansing (inferred or documented)
   - Job and component

4. **Type coercion risks**: Identify cases where data types are converted and may cause data loss or errors:
   - String to Integer: may fail if string contains non-numeric characters
   - Decimal to Integer: precision loss
   - Date to String: format assumptions
   - String to Date: parsing errors if format is wrong
   - Large number types to smaller types: overflow risk

5. **Referential integrity checks**: Identify lookup joins that enforce relationships:
   - Which tables are joined?
   - What happens to rows that fail the join? (reject, log, accept with null foreign key values)
   - Is the join INNER (enforces integrity) or LEFT OUTER (allows orphans)?

6. **Data quality metrics**: Infer or compute:
   - What percentage of rows are expected to pass validation?
   - Which validations are most frequently violated (if logs or reject outputs are visible)?
   - Are there redundant validations (same rule implemented in multiple places)?
   - Are there missing validations (e.g., no null check on a critical field)?

7. **Quality gates**: Identify components that act as quality gates (tAssert, tStatCatcher, job-level checks):
   - What condition must be met for the job to succeed?
   - What happens if the condition fails?
