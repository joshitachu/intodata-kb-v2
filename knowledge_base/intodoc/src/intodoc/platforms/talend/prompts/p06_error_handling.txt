You are analyzing a Talend integration project. Your task is to produce an **Error Handling & Resilience Analysis** — a thorough assessment of how each job handles failures, what happens when things go wrong, and where silent failures can occur.

## Talend Context
Talend provides several mechanisms for error handling, but many are optional and frequently misconfigured:
- **SUBJOB_ERROR trigger**: Fires when a subjob fails. If a subjob has no SUBJOB_ERROR connection, the error may be silently swallowed (the job continues) or cause an unhandled crash depending on the component and die-on-error settings.
- **COMPONENT_ERROR trigger**: Fires when a single component within a subjob fails. More granular than SUBJOB_ERROR.
- **tDie component**: Explicitly terminates the job with an error code and message. Connected via SUBJOB_ERROR or COMPONENT_ERROR. Used for controlled failure with a meaningful error message.
- **tWarn component**: Logs a warning message but does NOT stop the job. Used for non-fatal issues that should be recorded.
- **tLogRow component**: Prints data to the console/log. Often connected to error/reject flows to log problematic rows.
- **tLogCatcher component**: Catches all log events (tWarn, tDie, Java exceptions) and routes them to a flow for processing (e.g., writing to an error log table).
- **tStatCatcher**: Captures job execution statistics (start time, end time, row counts) for monitoring.
- **Die on error (component setting)**: Each component has a "Die on error" checkbox. When checked, any error in that component kills the entire job. When unchecked, the error is caught and can be handled by COMPONENT_ERROR or ignored.
- **DIE_ON_CHILD_ERROR (tRunJob setting)**: When a parent job calls a child job via tRunJob, this setting determines whether the parent dies if the child fails. If false, a child failure is silently ignored.
- **tTry / tCatch / tFinally**: Java try-catch-finally pattern components for explicit exception handling blocks.
- **Reject flows**: tMap and some components have "reject" output links that capture rows that failed processing (e.g., lookup misses, type conversion errors). If reject flows are not connected, failed rows are silently dropped.
- **Commit/rollback**: Database components can be configured with commit intervals and rollback-on-error behavior. Missing rollback configuration can lead to partial writes on failure.

## What to Extract

1. **Job-level error handling rating**: For each job, assign a rating:
   - **GOOD**: Has SUBJOB_ERROR handlers on critical subjobs, uses tDie for fatal errors, has tLogCatcher for centralized logging, reject flows are connected, database operations have rollback configured
   - **ADEQUATE**: Has some error handling but gaps exist (e.g., some subjobs lack error handlers, not all reject flows connected)
   - **POOR**: Minimal error handling — only die-on-error checkboxes, no explicit SUBJOB_ERROR handlers
   - **NONE**: No error handling mechanisms detected — all failures will either crash ungracefully or be silently ignored

2. **Error handling components**: For each job, list every error-related component:
   - tDie: where it is, what triggers it, what message/error code it produces
   - tWarn: what conditions trigger warnings
   - tLogRow: what data is being logged and why
   - tLogCatcher: whether present, what it captures, where it sends captured logs
   - tStatCatcher: whether present, where statistics are sent

3. **SUBJOB_ERROR connections**: Map every SUBJOB_ERROR trigger:
   - Which subjobs HAVE error handlers and what they do
   - Which subjobs are MISSING error handlers (these are silent failure risks)

4. **Die-on-error settings**: For each component:
   - Is "Die on error" checked or unchecked?
   - If unchecked, is there a COMPONENT_ERROR handler? If not, errors will be silently swallowed.

5. **DIE_ON_CHILD_ERROR in tRunJob**: For each tRunJob:
   - Is DIE_ON_CHILD_ERROR enabled?
   - If disabled, the parent job will continue even if the child fails — flag this as a risk.

6. **Reject flow analysis**: For each tMap and filterable component:
   - Are reject outputs connected to anything?
   - If not, how many rows could be silently dropped?
   - What kinds of failures produce rejects (lookup misses, type errors, null values)?

7. **Database transaction safety**:
   - Are database outputs configured with commit intervals?
   - Is rollback-on-error configured?
   - Could a failure result in partial data writes (some rows committed, others not)?

8. **Silent failure scenarios**: Identify specific scenarios where a failure would go completely unnoticed:
   - Subjob fails but no SUBJOB_ERROR handler and next subjob runs via separate trigger chain
   - tRunJob child fails but DIE_ON_CHILD_ERROR is false
   - tMap reject rows dropped silently
   - Die-on-error unchecked with no COMPONENT_ERROR handler
