You are analyzing a Talend integration project. Your task is to produce a **Cross-Region Analysis** — compare and contrast patterns, architectures, data flows, and business logic across multiple geographic regions (BRA, ITA, JPN, SAF, USA) to identify standardization opportunities, regional deviations, and best practices.

## Talend Context
Vaxxinova operates in 5 regions, each with its own Talend jobs following the pattern `{REGION}_{SUBSIDIARY}_{LAYER}_{VERSION}`:
- **BRA** (Brazil) — **VBR** (Vaxxinova Brazil)
- **ITA** (Italy) — **VAX** (Vaxxinova Italy)
- **JPN** (Japan) — **VJP** (Vaxxinova Japan)
- **SAF** (South Africa) — **VSA** (Vaxxinova South Africa)
- **USA** (United States) — **NPL** (Newport Labs)

Multi-region integration projects often have:
- **Shared architecture patterns**: All regions follow RAW -> CLEAN -> PUBLISH pipeline
- **Regional deviations**: Different source systems, different business rules, different data schemas
- **Global orchestration jobs**: GLOBAL_* jobs that call regional jobs in parallel or sequence
- **Standardization opportunities**: Duplicated logic that could be refactored into shared routines, joblets, or parameterized jobs
- **Best practices**: One region may have better implementations (error handling, validation, performance) that could be adopted by others

## What to Extract

1. **Regional job inventory**: For each region:
   - Total job count
   - Jobs by layer (RAW, CLEAN, PUBLISH)
   - Jobs by domain (Sales, Finance, HR, etc.)
   - Unique job patterns not found in other regions

2. **Architectural patterns by region**: For each region:
   - Pipeline structure (RAW -> CLEAN -> PUBLISH, or variations)
   - Orchestration approach (Global master job, independent scheduling, etc.)
   - Source systems (MSSQL, Oracle, SAP, API, files, etc.)
   - Target systems (BigQuery datasets, data lake, data warehouse, etc.)
   - Metadata management (REPOSITORY vs BUILT_IN)

3. **Data flow patterns**: Compare how each region moves data:
   - Source to target mappings (MSSQL -> BigQuery, Oracle -> BigQuery, etc.)
   - Transformation layers (how many, what they do)
   - Data volume estimates (which region has the most data?)
   - Batch frequency (nightly, hourly, real-time)

4. **Business logic comparison**: For each region, identify:
   - Status code mappings (do all regions use the same codes? 'A' = Active, etc.)
   - Data validation rules (are null checks consistent?)
   - Data cleansing patterns (TRIM, UPCASE, date formatting)
   - Calculation formulas (revenue calculations, aggregations)
   - Default values (what value is used for nulls?)

5. **Regional deviations**: Identify differences that may indicate bugs, inconsistencies, or intentional regional variations:
   - Schema differences (same logical entity, different column names or types)
   - Business rule conflicts (same concept, different implementation)
   - Naming convention violations (one region doesn't follow standard)
   - Missing jobs (one region has jobs that others don't — should they?)

6. **Shared vs unique components**: Categorize components:
   - **Shared patterns**: Components/logic that appear in all or most regions (e.g., all regions have RAW layer jobs that read from MSSQL and write to BigQuery)
   - **Unique patterns**: Components/logic found in only one region (e.g., only USA has API integration jobs)
   - **Partially shared**: Logic that appears in some regions but not all (e.g., only BRA and ITA have data masking for SSN)

7. **Standardization score**: Rate how consistent the regions are (1-10):
   - Naming conventions
   - Architectural patterns
   - Business logic
   - Data schemas
   - Component configuration

8. **Best practices by region**: Identify which region has the best implementation in each area:
   - Error handling: which region has the most robust error handling?
   - Performance: which region has the best batch sizes and database pushdown?
   - Security: which region has the best credential management?
   - Data quality: which region has the most comprehensive validation?

9. **Refactoring recommendations**: Suggest how to standardize:
   - Which logic should be extracted into shared routines or joblets?
   - Which regional jobs could be replaced with a single parameterized job?
   - Which deviations should be standardized vs preserved as intentional regional differences?

10. **Region comparison Mermaid diagram**: Generate a visual comparison of region architectures, data flows, or job counts.
