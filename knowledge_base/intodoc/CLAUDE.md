# intodoc -- Integration Documentation Generator

> **Note:** This file describes the intodoc CLI scanner. For the MCP-based documentation
> agent workflow (which is the current primary doc generation method), see `knowledge_base/CLAUDE.md`.

## What is this?
A Python CLI tool that scans integration codebases (Talend, MuleSoft, dbt, etc.) and produces structured scan data. Originally included LLM-based analysis and Jinja2 doc generation; documentation is now generated by the Claude Code agent via MCP (see `knowledge_base/CLAUDE.md`).

## Quick Start
```bash
cd intodoc
pip install -e ".[dev]"
intodoc scan <source-dir> --platform talend --output-dir ../intodoc-output
```

  - **Generic**: Universal fallback, extension-based classification, directory-based job grouping
- **Shared prompts**: 12 platform-agnostic prompts in `_shared/prompts/`, overridable per platform
- **BaseDistiller**: Common chunking logic (~30K token chunks), extended by TalendDistiller/WorkatoDistiller/LobsterDistiller
- **12 consolidated reference docs** (00-11): Define output format/depth for the documentation agent
- **Doc generation**: Now handled by Claude Code agent via MCP server (not CLI analyzer)
- **Legacy CLI path**: 21-pass LLM analyzer + 32 Jinja2 templates still exist but are not the primary workflow
- **PDF + Qdrant export** functional (legacy CLI path)
- **Two-layer credential filter**: Text regex + post-parse structural redaction (standard/strict/paranoid)
- **ProjectManifest** provides cross-job context to all passes
- **Universal IR** normalizes to platform-agnostic representation (99.4% expression parse rate)

## Current Custom Harness Notes (May 2026)

- MCP custom documentation generation now runs through a bounded internal agent runtime in `mcp-server/src/mcp_server/providers/custom/agent_runtime.py`.
- The runtime persists task contracts and exact LLM-authored outputs under `docs_staging/_agent_tasks/{phase}/{target_id}/`, including validation reports, tool ledgers, provider metrics, and accepted/rejected status.
- Phase 2 is group-agent based with configurable concurrency (`MCP_AGENT_PHASE2_CONCURRENCY`, default 6). Split group work is merged by an LLM merge task, not by Python-authored summaries.
- Phase 2.6 scorecard and Phase 3 documents are also agent tasks. Phase 3 defaults to one document agent per required markdown doc with concurrency cap `MCP_AGENT_PHASE3_CONCURRENCY` (default 4).
- Validator gaps now create targeted repair tasks where possible before the run fails.
- Python supervises scanning, contracts, budgets, validation, retry/repair, cache/resume, and publish only. LLM agents author analysis and documentation prose.

## Steven Generic-Scanner Note

- Project `Steven` exposed a generic-platform documentation gap: generated docs claimed `Web.config` and `Global.asax.cs` were unavailable, while local source and `scan_result.json` contain them.
- `Web.config` includes sensitive app settings and database connection strings; never copy raw values into prompts, logs, docs, or memory. Keep using credential redaction.
- `Global.asax.cs` contains ServiceStack/OrmLite setup and named database connection registrations. Future scanner/EngineeringFacts work should expose redacted connection names and app-setting keys so docs can say which runtime connections exist without leaking credentials.
- The bug is downstream synthesis/evidence surfacing, not source absence: generic docs relied on normalized maps that only showed file paths and dependencies, missing the richer redacted source evidence already present in the scan cache.

## Key Architecture
- **Platform-explicit**: user declares `--platform talend|workato|lobster|generic` -- loads platform-specific parser, prompts, best practices
- **Platform plugins**: `src/intodoc/platforms/<name>/` -- each is self-contained (Talend, Workato, Generic)
- **Inheritance**: `PlatformPlugin -> GenericPlugin -> WorkatoPlugin/LobsterPlugin`, `BaseDistiller -> TalendDistiller/WorkatoDistiller/LobsterDistiller`
- **Prompt resolution**: Platform-specific prompts override `_shared/prompts/` fallback
- **Dual doc generation**:
  - **Primary (MCP agent)**: Claude Code reads prompts + fetches chunks via MCP, writes .md docs directly
  - **Legacy (CLI)**: 21-pass LLM analysis via LiteLLM API + 32 Jinja2 templates
- **Universal IR**: `intodoc normalize` converts ScanResult to platform-agnostic NormalizedProject

## Project Layout
- `src/intodoc/cli.py` -- Click CLI entry point (scan, normalize, analyze, generate, export, run)
- `src/intodoc/config.py` -- Pydantic Settings configuration
- `src/intodoc/models.py` -- ALL shared Pydantic data models (30+)
- `src/intodoc/ir/` -- Universal Intermediate Representation (models, expression_parser, normalizer, dag, persistence, pseudocode, validator, type_inferrer, llm_enrichment)
- `src/intodoc/scanner/` -- file walking, git analysis, credential filtering
- `src/intodoc/platforms/` -- platform plugins (talend/, workato/, generic/, _shared/)
- `src/intodoc/platforms/base_distiller.py` -- shared chunking logic for all platforms
- `src/intodoc/chunker/` -- group jobs into LLM-sized chunks
- `src/intodoc/analyzer/` -- LLM client, passes (21), cost tracking (legacy CLI path)
- `src/intodoc/generator/` -- Jinja2 markdown rendering, 32 templates (legacy CLI path)
- `src/intodoc/exporter/` -- PDF and Qdrant export
- `reference-docs/` -- 25 example .md files (format/structure spec for doc agents)

## Known Pitfalls
- **Windows encoding**: Unicode chars (em-dashes, arrows) break on cp1252 -- use ASCII in CLI text
- **Token bloat**: tMap distiller MUST strip noise BEFORE chunking -- field_type filtering is critical
- **ENDPOINT preservation**: Don't strip URL-related params -- REST/OData endpoints are semantically important
- **Connection matching**: Use component `REPOSITORY_PROPERTY_TYPE` refs, NOT region-name matching
- **hatchling**: Use hatchling build system, NOT setuptools -- pyproject.toml is configured for it
- **Budget**: Default $5 limit for legacy CLI analyzer -- 18 passes on 9 chunks can exceed this with larger models

## Rules
- Always read `.agent/README.md` before planning work
- Always read `.claude/context.md` and `.claude/PROGRESS_LOG.md` before coding
- Log EVERY change to `.claude/PROGRESS_LOG.md` -- this includes doc generation runs, architecture changes, new prompts/reference docs, and bug fixes
- Update `.agent/` docs when architecture/models/config changes
- Run credential filter BEFORE any LLM calls -- never send raw credentials to API
- Legacy CLI analyzer: claude-sonnet for passes 1-17, opus for pass 18 (synthesis)
- Legacy CLI hard budget limit default: $50
- **No workarounds** -- fixes must address the root cause, not suppress symptoms. If a proper fix requires broader changes, make them. Never ship a narrow patch when the defect pattern exists elsewhere in the codebase.
- **Generalize fixes** -- before fixing anything, check whether the same failure can occur in other places. Fix it at the level that prevents all recurrences. One-off special-case branches are not acceptable solutions.
- **Use design patterns** -- before writing a new class, service, or module, identify whether an established pattern fits (Strategy, Repository, Factory, Observer, Pipeline, etc.). Don't invent bespoke structures when a well-understood pattern solves the problem.
