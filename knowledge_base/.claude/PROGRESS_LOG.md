## Session: 2026-09-14 -- OpenCode runs no longer die on a JSON event larger than the stream buffer

- **Files changed by this work**: new `mcp-server/src/mcp_server/utils/stream_frames.py`; `mcp-server/src/mcp_server/providers/opencode_cli.py`; `mcp-server/src/mcp_server/connectors/mcp_facade.py`; new `mcp-server/tests/test_utils/test_stream_frames.py`; `mcp-server/tests/test_providers/test_opencode_cli.py`. `git diff --stat HEAD` reports ~1.8k deletions across the two files that already existed -- those belong to the earlier uncommitted session in this tree, not to this work.
- **Problem**: generating `ettm_TEST_Claude` with OpenCode failed ~43 s in, at the `provider` phase, with `Separator is found, but chunk is longer than limit` (recorded in `output/ettm_TEST_Claude/docs_staging/_run_manifest.json`, run 257, model `opencode-go/minimax-m2.7`). `_analysis/` was empty; the UI reported only "Generation failed but staging is preserved".
- **Root cause**: `consume_stdout` read the `opencode run --format json` event stream with `async for raw in process.stdout`, which is `StreamReader.readline()` and is bounded by the reader's buffer limit (asyncio's default 64 KiB). One event carries a whole tool result -- a subagent report, a file read -- so its size is set by the model, not by the protocol. The first event past 64 KiB raised `LimitOverrunError`, `readline()` converted it to `ValueError`, and since `run()` catches only `TimeoutError`/`CancelledError`/`OpenCodeCompatibilityError`/`OSError`, it escaped and failed the whole run. The log's `task` and `bash` tool calls are exactly the events that exceed it. `consume_stderr` had the same defect, and so did the connector facade's `_bridge_request`, which read broker responses over `open_unix_connection` at the **default** limit while the server it talks to was configured at 1 MiB.
- **Change**: added `utils/stream_frames.py` -- `iter_frames()` reads raw chunks and splits on newlines itself, so the buffer limit stops being a ceiling on frame size, and the one remaining bound is explicit: a frame beyond `max_frame_bytes` is dropped with its byte count reported and the stream resynchronises on the next frame. `read_frame()` is the request/response variant, raising the typed `OversizedFrameError` because a truncated payload is not usable. Wired into both OpenCode readers (16 MiB per event, 1 MiB per stderr line) and both ends of the facade relay (1 MiB request, 4 MiB response, mapped to the existing `connector_denied` answer). Per-event processing in `consume_stdout` is now failure-isolated: that lane is telemetry, and the documents themselves reach staging through the session's file tools.
- **Why this approach**: widening the buffer (`limit=` on `create_subprocess_exec`) alone was rejected -- it only moves the cliff, and the frame size is model-controlled so no fixed buffer is a guarantee. The buffer is still raised to 4 MiB, but purely as a throughput knob; the regression test pins it back to asyncio's 64 KiB default so the fix cannot pass for the wrong reason. Dropping an oversized event rather than failing was chosen because these events carry usage accounting, not documentation -- the cost is a gap in token totals, not lost output.

The new `test_json_event_larger_than_the_stream_limit_does_not_fail_the_run` was confirmed to reproduce: reverting `consume_stdout` to `async for raw in process.stdout` fails it with `ValueError: Separator is not found, and chunk exceed the limit` (the sibling message from the same `LimitOverrunError` conversion, differing only by whether the newline was already buffered). `ruff check` clean on all changed files except two pre-existing findings in `opencode_cli.py` (`S110`/`BLE001` at the timeout handler's `try/except Exception: pass`), untouched here.
