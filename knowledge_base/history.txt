❯ and why not no mini models from openai for example?                           

⏺ Fair challenge. Two reasons GPT-4o mini was deprioritized over Gemini 2.5
  Flash at similar cost:

  1. Context window
  GPT-4o mini caps at 128K tokens. The harness hard ceiling is 120K — so you are
   right at the edge with zero headroom. Gemini 2.5 Flash has a 1M token context
   window, which gives the evidence-loading logic room to breathe without
  hitting truncation edge cases. One large evidence set and mini starts dropping
   content.

  2. Reasoning quality for the same price
  Gemini 2.5 Flash uses an internal thinking budget — it's not a "mini" in the
  distilled sense, it's a full reasoning model at flash pricing. GPT-4o mini is
  genuinely a smaller, distilled model optimised for throughput, not synthesis
  depth. For Phase 3 narrative docs (the gap you're trying to close), you need
  reasoning, not speed.

  ---
  Where OpenAI does make sense: o4-mini

  If you want OpenAI in the stack, the right pick is o4-mini, not 4o-mini —
  different model entirely:

  ┌─────────────┬───────────┬───────────┬────────────┬───────────┬─────────┐
  │    Model    │   Type    │ Input $/M │ Output $/M │ Reasoning │ Context │
  ├─────────────┼───────────┼───────────┼────────────┼───────────┼─────────┤
  │ GPT-4o mini │ Distilled │ $0.15     │ $0.60      │ No        │ 128K    │
  ├─────────────┼───────────┼───────────┼────────────┼───────────┼─────────┤
  │ o4-mini     │ Reasoning │ $1.10     │ $4.40      │ Yes       │ 200K    │
  └─────────────┴───────────┴───────────┴────────────┴───────────┴─────────┘

  o4-mini is OpenAI's cost-efficient chain-of-thought model. At $4.40/M output
  it is more expensive than Gemini Pro ($10/M output) but its reasoning profile
  is competitive and it handles complex synthesis well. Could work as a Phase 3
  alternative to Gemini 2.5 Pro if you open an OpenAI account. One account, one
  key — same tradeoff as Google.

  Short answer: GPT-4o mini is the wrong tool for this job. o4-mini is worth
  considering as a Phase 3 option alongside Gemini 2.5 Pro.

⏺ Here is what the audit found. There are four structural gaps in Phase 3, one
  of which is severe enough that it likely explains most of the low narrative

  ---
  The Critical Finding: Prompt Pack Silently Drops Phase 2

  In harness.py, _phase3_context_files():

  if prompt_pack.exists():
      files.append(prompt_pack)
      return files   # ← Phase 2 bundle never reaches Phase 3

  When a _phase3_prompt_pack_*.md exists, the function returns immediately — the
   Phase 2 _bundle_*.md is never included. The agent starts with only a
  structural template and zero synthesised analysis. It has to reconstruct
  everything from scratch within 12 tool calls.

  The steven_harness run scored well precisely because it had no prompt packs —
  so the fallback path ran correctly and included the bundles. Runs with prompt
  packs silently lose all Phase 2 context.

  ---
  The Other Three Gaps

  1. Bundle files 318KB, readable budget ~80KB — bundles are hinted not
  pre-loaded, and tool byte limits mean the agent can only consume ~25% of the
  bundle content even if it tries.
  2. 3 of 12 tool calls wasted on directory listing — agents enumerate
  _preprocess/, _analysis/, _assessment/ before reading anything useful.
  3. Same evidence scope for all doc types — executive summary and architecture
  map get identical allowed_groups, no guidance on relevance.

  Recommended Order

  1. Fix 1 first — remove the early return in _phase3_context_files() so bundle

⏺ Let me walk through it end to end.

  ---
  Step 0 — The Scanner

  Before any doc generation happens, the intodoc scanner has already run. It
  parsed your integration source code (Talend jobs, Workato recipes, etc.) and
  produced a scan_result.json — a structured cache of everything it found: jobs,
   connections, transformations, data flows, dependencies, config values. This
  is the raw material. The doc generation never touches the source code directly
   — only this cache.

  ---
  Step 1 — Investigation (Phase 1)

  A single LLM agent reads the scan cache at a high level and produces an
  investigation summary — what kind of project is this, how many units, what are
   the major groups, what are the main patterns. Think of it as a project brief.

  Output: _investigation/*.md files in the staging directory.

  ---
  Step 2 — Group Analysis (Phase 2)

  This is the heavy lifting. The scanner organises integration units (jobs,
  flows, etc.) into groups — logical clusters like "CRM sync jobs" or "Order
  processing flows."

  For each group, one LLM agent task is dispatched. Up to 6 run in parallel.
  Each agent:
  - Gets a contract defining which units and evidence categories it can access
  - Has 12 tool calls to pull evidence (job details, connections,
  transformations, dependencies)
  - Writes a structured analysis of that group: what it does, how it connects to
   other systems, data flows, risks, patterns

  Output: one analysis markdown file per group, stored in _analysis/.

  This is where connections are made — the agent has bounded access to one
  group's evidence and synthesises what it means.

  ---
  Step 2.6 — Scorecard

  After all groups are analysed, a separate agent reads all the Phase 2 outputs
  and produces a quality/risk scorecard — a consolidated risk register, severity
   counts, flags.

  Output: _assessment/scorecard.md

  ---
  Step 2.8 — Bundle Assembly

  This is a Python step, not an LLM step. The harness takes all the Phase 2
  group analysis files and sorts them into three bundles by which final
  documents they feed:

  - _bundle_core.md → feeds architecture, component inventory, data flows, agent
   brief
  - _bundle_business_ops.md → feeds business rules, config, operations/security
  - _bundle_patterns_user.md → feeds patterns, scorecard doc, change playbook

  Each bundle is a single large markdown file (~318KB) containing all the
  relevant Phase 2 analysis concatenated together. This is what Phase 3 is
  supposed to start from.

  ---
  Step 3 — Document Writing (Phase 3)

  There are 9 final documents to produce. For each one, an LLM agent task is
  dispatched. Up to 4 run in parallel. Each agent:
  - Gets the relevant bundle (Phase 2 analysis for that doc family)
  - Gets the scorecard
  - Gets a prompt pack or template telling it the structure and requirements of
  that document
  - Has 12 tool calls to fetch any additional evidence it needs
  - Writes the full markdown document (up to 32K tokens)

  The 9 documents range from technical (architecture map, component inventory,
  data flows) to narrative (agent brief/executive summary, change playbook).

  Output: final .md files written to docs_staging/.

  ---
  Step 4 — Validation and Swap

  The harness validates each document (coverage checks, required sections,
  minimum depth). If a doc fails validation it is retried (up to 2 attempts).

  Once all 9 docs pass, the staging swap happens:
  - Old docs/ is removed
  - docs_staging/ is renamed to docs/
  - The docs are pushed to the RAG vector database automatically

  If any doc fails both attempts, the swap does not happen — the old docs/ stays
   intact.

  The pipeline depends on Step 2.8 → Step 3 working correctly: bundles produced
  in 2.8 must reach Phase 3 agents as their starting material.

  The bug is in Step 3. When a prompt pack template file exists on disk, the

   nothing else. It has to use its 12 tool calls to rediscover everything Phase
  2 already analysed, instead of synthesising from the bundle. The result is
  shallower docs because it runs out of tool calls before it can go deep.
